## 結論(一句話)
鏡像**成立且可獨立重現**,但與 PDF 無關(不匯入 PDF 的對照組也一樣鏡像);原因是「輪廓編輯圖 u→/v↓」配上放置表單預設 `u +x · v +y`(法向 +Z「天花」),在俯視(沿 −Z,+Y 朝上)下必然上下翻轉,這是 GEO-244 有記載的設計:偵測到後只提示、只提供「依原圖對齊放置方向」,**刻意不自動改**。**77.647 m³ 這部分是錯的推論**:鏡像不改體積;77.647 來自 T2 拿來比較的是另一個輪廓(半自動候選 5988/4987/1988/2002),不是鏡像造成的。

## 2. 鏡像的具體(哪個軸)
- 編輯圖:螢幕右 = +u,螢幕下 = +v(面板文字「輪廓編輯圖沿局部 u→、v↓」;游標讀數往下 v 變大)。
- 放置(預設):world = origin + u·x_local + v·y_local(model-viewer.js:45),所以 X = u、Y = v。
- 俯視:螢幕右 = +X、螢幕上 = +Y。所以**編輯圖的「下」變成俯視的「上」**:翻的是 Y(南北),X(東西)不動。
- A 組實際頂點(局部 = 世界,因為原點是 0、u+x、v+y):L6 (11500,2000) 在編輯圖左上 → 世界 Y 最小 → 俯視**左下**;缺口局部 u 15500–17500、v 2000–4000 → 世界 Y 2000–4000(最低)→ 俯視**右下**。
- 對齊之後,放置表單讀到 origin (0, 9000, 0)、u +x、v −y(9000 = 局部 v 的 min+max = 2000+7000):Y = 9000 − v,L6 → (11500,7000) 左上,缺口 Y 5000–7000 → 右上;世界外框不變(X 11500–17500、Y 2000–7000);標籤從「天花」變成「地板 z=0」。
- 空間建模邊編號圖 `#smPlanOutline`:未對齊 `M32,143 L124,143 L124,97 L170,97 L170,28 L32,28`(第 1 邊在底部);對齊後 `M32,28 L124,28 L124,74 L170,74 L170,143 L32,143`。A、B 兩組未對齊時的 path 一字不差。

## 3. 77.647 m³ 怎麼來的
- 我核對的是 `#smVolume` 空間體積、`#smClearance` 扣除後淨空、`#smWallVolume` 材料牆。用精確 L 形時,鏡像與對齊兩種情況都是 **78 / 78 / 6.72**,鏡像沒有改變體積。
- T2 的 148/149 用的是另一個面:T2 147-placement-ui.png 的外環邊是 4000/2002/1988/2985/5988/4987(半自動候選)。面積 = 5988×4987 − 1988×2002 = 25,882,180 mm²;乘 3000 = **77.6465 m³**,正好等於 77.647。材料牆:周長 2×(5988+4987) = 21,950;21,950×100 + 4×100² = 2,235,000 mm²,乘 3000 = **6.705 m³**,正好等於 149 的 6.705。
- 所以形狀本身沒有變形,牆也沒有加厚到錯的方向,也沒有任何面被誤判:8 面全是「+1 實際邊界」,底面 −1(V22-faces-list.png)。T2 拿來對照的 096(78 m³)是另一個精確 L 形的面,兩邊不能直接比。「77.647 ≠ 78 證明幾何不只是翻轉」**不成立**。
- 半自動候選本身比圖面少 12/13 mm(5988 vs 6000)是另一件事(線寬/取邊),不在本題範圍,未追查。

## 5. 原因追查
- 已確認 `geometry-web/app.js:8426-8433`:PLACE_PRESETS「天花」= u +x、v +y,「地板」= u +y、v +x。
- 已確認 `app.js:8516-8517`(placeFormHTML):新面沒有 surf 或 slot 時,u/v 下拉預設 `"+x"`/`"+y"`,也就是「天花」(法向 +Z)。表單只做 u⊥v 檢查(`app.js:8525-8546` updatePlaceValid),不知道這個面有底圖、也不知道它預計當俯視平面用。
- 已確認 `geometry-web/model-viewer.js:52-63` drawingAlignment:`changed = normalZ !== (view==='top' ? -1 : 1)`(:59)。法向 +Z 配俯視一定 changed;修正方式是 v 反向,原點加 (minV+maxV)·v。
- 已確認 `geometry-web/space-workspace.js:219-224`:要先有已保存的投影定義(validProjection)才會算 alignment,才顯示警示文字。所以第一次按「確認用途與觀看方向」時看不到任何方向警告(V1 實測 v0 的說明文字是一般說明)。`:433-451`:只有第二次按、而且觀看方向相同時才會 mutate 放置。`:454`:第一次只寫投影定義,不改放置。預覽與建立按鈕不受未對齊影響(實測 `#smPreview` enabled、建立成功)。
- 已確認 docs:`geometry-web/docs/FACE-PROJECTION.md:25`(編輯圖保持 u→/v↓,改觀看方向不翻轉輪廓、不移動放置)、`:33`(不一致時提供「依原圖對齊放置方向」,「僅設定觀看方向仍只保存用途資訊,不會自動改動放置」);`docs/SPACE-MODELING.md:32` 同義;`BACKLOG.md:4186-4190` GEO-244 明寫「投影定義本身仍只保存用途資訊,不自動搬移既有場景」。
- 公理層.md:D2(:37)只定義 frame U×V=N;:433 的 u→/v↓ 是錨點條文。**沒有任何條文規定「放置預設值要和描繪圖方向一致」或「平面投影必須對齊原圖」= 無規格**。UI-REDESIGN-PLAN.md:174 只列六個預設,沒有說新面要選哪一個。
- 推論:「天花 u+x v+y」在語意上等於「從下往上看這張圖」(編輯圖視線 = u×v = +Z,跟面板顯示「投影視圖(仰視)」一致)。拿一張俯視平面圖照預設放置,等於把它當成天花仰視圖;產品知道這是矛盾,但把決定留給使用者。
- 推論:PDF 的 y 向上和世界 +Y 之間沒有轉換錯誤。底圖在編輯圖上是正立的(ROOM_L 缺口右上),不用 PDF 的對照組也有同樣結果,所以問題完全出在「編輯圖 v↓ ↔ 預設放置 V=+Y ↔ 俯視 +Y↑」這一段。

## 6. 判定
- **鏡像現象:確認重現(信度高,0.95)**,A、B 兩組都會發生。原因在放置預設與編輯圖方向,不在 PDF 座標轉換。
- **分類:設計如此(GEO-244 明文:偵測、提示、提供按鈕,但不自動對齊),外加次要體驗缺口;不判「資料錯誤」(信度中,0.7)。** 理由:程式算出的幾何忠於放置座標,體積/牆量都正確,規格明說對齊由使用者決定,預設值也無規格。體驗缺口有三點:(a) 放置表單對有底圖的面仍預設「天花」,沒有任何方向提示;(b) 方向警告要等第一次確認之後才出現;(c) 不對齊也能預覽、建立,並把鏡像的模型連同「俯視」定義存進模型庫。
- 給產品決策的風險說明:如果產品意圖是「描底圖 → 照預設 → 得到跟原圖同手性的模型」,這就會升級成資料錯誤(多房間或要對真實方位時會錯)。這需要使用者拍板,不是驗收員能定的。
- **T2-05 的「77.647 m³ 代表幾何不只翻轉」:駁回(信度高,0.95)。** 這是不同輪廓的算術結果(25.88218 m² × 3 m;牆 6.705 也吻合),與鏡像無關。
- 已知對照:屬 GEO-244 / #117(closed)/ PR #121 的已知設計範圍(known-issues 第 55 行、5.3/5.4 節);#117 修的是「提供對齊」,沒有改成「預設對齊」。
