# 畫布參數卡驗收（GEO-223）

日期：2026-09-30。依據為已核准的 D31／I38／I39／R33 與 [操作契約](../../geometry-core/PARAMETERS-CONTRACT.md)。GEO-224 重做編輯面板後，完整介面回歸 1503 通過斷言（GEO-223 時為 1482，差額為 GEO-224 新增的 21 條 P76 斷言）、0 失敗、0 略過群組，其餘下列檢查亦通過。

## 已驗證流程

- 真實介面建立 `(915,1830)`、排格算式及 `W27H33`，草稿先列出欄位和單位。
- 無限網格引用跨卡算式；改板寬先列出新舊值、使用處與間接受影響網格，確認前世界不變，確認及一次復原／重做涵蓋全部依賴。
- 角材 A／B 明選 W／H，有限面材網格引用板寬；從使用物件跳回參數卡，完整專案保存重開後仍保留欄位身分。
- 精確分數、跨卡及同卡算式、括號、負值、數量／比例、Unicode 運算符；缺件、循環、單位、除零、容量及精度錯誤整筆拒絕。
- 457.5 mm 可保存；直接套入整數幾何拒絕，乘 2 得整數後可用。舊參考式保持原取下界行為。
- 改名／重排不改引用，被使用欄位不可刪；解除工程來源引用保存當下有效值。畫布移動不使候選失效，定義變更使候選失效。
- 實際下載參數包包含整卡依賴、排除有效值快取與幾何；匯入先預覽新增卡片，同名／重複匯入不覆寫，原卡修改不改副本。
- 草稿阻擋保存；較舊試算及定義改動前尚未回覆的候選不能覆蓋現況。手機 390px 控制至少 44px，沒有水平溢出。
- GEO-224 編輯面板（設計稿 4a、Q25 🔒）：三顆範本鈕與快速輸入預告；每欄顯示核心試算值，`=1/0` 只標出錯欄並顯示「除以零」、確認鈕停用；引用晶片排除自己與會造成循環的來源，點晶片插入引用後試算成功；1280px 面板在畫布右側、確認鈕固定在面板可視範圍（頁尾 sticky），離開後其他檢視器仍在畫布下方；390px 所有可點控制 ≥44px、無水平溢出；建立新卡時畫布出現虛線草稿卡，捨棄後消失且保存內容不變（`parameter_workflow_test.js` 的 GEO-224 區段）。
- 共用基準引用參數欄位時，即使沒有下游構件仍先出現連動預覽；取消保持原狀，確認後保留 `param:卡:欄` 來源與座標，基準列可跳回參數卡（`parameter_workflow_test.js:118-128`）。
- 面內參考線同樣：選參數來源建立引用線，沒有角材引用時仍先預覽；取消不建線，確認後保留來源、軸向與 1830 mm 位置，來源旁的按鈕可跳回參數卡（`parameter_workflow_test.js:132-145`）。
- `.gcanvas` /6 保留參數能力，/1–5 繼續讀取；建模來源保留未使用分數卡與完整引用，不以數字降級。混合工程／參數能力按固定順序核對。

依賴深度（已修，原缺口記錄如下）：舊實作只在求值堆疊實際走到第 65 層時才拒絕，且欄位求值有快取；最深的鏈排在儲存順序前面時 64 合法、65 被拒，但依賴端排在前面時 65、120、256 層全被接受，且 65 層拒絕訊息被路徑前綴擠出錯誤緩衝而看不到 `UNSUPPORTED/CAPACITY`。現行做法：深度是欄位自身的屬性（葉為 1，其餘為 1＋所引用欄位的最大深度），完成求值時記下、被引用時（含快取命中）讀回，與儲存順序無關；錯誤路徑前綴改由 `parameter_wrap_error` 組裝，路徑過長時保留最外層、最內層與根因並省略中段，總長不超過 190 bytes，錯誤碼恆可見。驗證（core:293–318）：深鏈在前與葉在前兩種儲存順序，各測 1、63、64 層合法，65、120、256 層拒絕且訊息含 `UNSUPPORTED/CAPACITY: dependency depth exceeds 64`；另測「64 層鏈全數已快取後，再掛一個依賴鏈頂的欄位」＝65 層必拒、63 層鏈同款＝64 層合法（專打快取命中不帶深度）；再加扇入案例：一個欄位同時引用 63 層鏈頂與葉＝64 層合法、引用 64 層鏈頂與葉＝65 層必拒，兩種引用順序都測（專打「深度誤寫成累加」與「遞迴進出時 maxref 未還原」；舊 bridge 上 64+葉的兩個案例紅）。未修的舊 bridge 上此測試 7 個子案例全紅。本機 Smart App Control 擋下新編的 Windows core.exe 後，改以 WSL／GCC 當版核心完成重跑：136/136 場景通過，無斷言失敗或環境失敗。另外，核心的 128 節點上限在 2047 bytes 紀錄上限之前無法用合法輸入到達（30 個字面值的加總就先超過位元組上限，20 個仍合法），因此只驗證「129 節點被拒」與「20 個字面值合法」。

CDP 數量為斷言數，涵蓋實際滑鼠／鍵盤、DOM 檢查及原生 API；不是端到端情境數。最終原生驗證使用 WSL／GCC 當版 bridge／core／model-base；完整 CDP 與 97 項 JavaScript 測試使用當版 Windows bridge 與既有可執行的 model-base。當版 model-base 的驗證由 Linux 原生測試涵蓋；P76、P68 與 P27 摘錄亦在當版 WSL 服務上通過。兩種服務均由 Windows Chrome 操作。執行檔、測試服務與回報目錄皆在暫存目錄，獨立於使用者場景。過程中的舊核心欄位相容、能力順序、舊選單順序及測試 DOM 替身問題均修正後重驗。

WSL 介面驗證暴露三處測試過早讀取畫面的問題：P27 在核心尚未完成命中與開啟歷史群組前檢查拖曳；P68 在復原的畫面刷新完成前導航；P76 則把上一張卡的名稱欄當作新表單已載入。測試改為等待實際拖曳狀態、完整刷新與新表單出現，保留原有操作和所有斷言；修正後上述 WSL 專項全綠，完整回歸由 Windows 服務完成。本輪未再跑第二次 WSL 完整回歸。
