§0 · 先建立心智模型

三套座標系，一條資料流

整份程式 9,073 行，但骨架只有一句話。所有東西都活在三套座標系裡，再由一條資料流串起來。單位一律 mm，全部用 64 位元整數，所以相等比較和叉積都是精確的，沒有浮點誤差。

  • 房間座標 (x, y, z)：X 向右、Y 向房間深處、Z 向上。所有最終答案都用它表達。
  • 表面 UV 座標 (u, v, w)：只存在於某一片空間邊界面上。天花板的 u 對應房間 X、v 對應房間 Y、w 沿法線離開表面。
  • 角材局部座標 (長度, A, B)：只存在於某一支角材上。A 是 27、B 是 33、長度是 L。
表面定義→ 推導四條邊→ 放兩條參考線→ 交點當錨點→ 造一支角材→ A0 面貼到錨點→ 推導六個面→ 印文字→ 印 SVG
最重要的設計決定：只存「定義」，不存「推導結果」。邊不存端點、參考線不存線段、角材不存八個角，全部在需要時從父物件算出來。改一個數字，所有推導自動跟著對。
§1 · 基礎幾何型別 / 向量運算

兩個長得一樣的結構，四個小函式

Point3 和 Vector3 欄位完全相同，分開命名只是為了讓讀者一眼知道「這是位置」還是「這是方向」。Coord 是 int64_t：整數座標讓後面的「軸長是否為 1」「兩軸是否正交」都能用 == 判斷。

向量運算只有四個。點積用來檢查長度與正交，叉積用來檢查與建立右手座標，後面會反覆看到。

§2 · 空間邊界面

一個原點、三個軸，一條公式

空間邊界面就是「房間裡的一片矩形」，例如天花板。它的核心是 SurfaceFrame：原點加三個單位軸。任何表面上的東西要變成房間座標，都經過同一條公式：

room = origin + u·axis_u + v·axis_v + w·normal

§3 · 邊界面與承載面：輪廓環推導邊

邊不再是物件，是環上的一段

SpaceBoundarySurface 是純局部 2D：一個正交外輪廓 PolygonLoop2、零個以上的孔、每條邊的 fixity（FIXED／FREE）。它不知道自己在世界哪裡；3D 位置由承載面 PlacementSurface 的 frame 提供。邊不再獨立宣告——第 i 條邊就是 outline.v[i] → outline.v[i+1]，fixity 存在環上。

§4 · 表面參考線

一條線只記方向和一個 offset

參考線不是實體，只是定位工具。沿 U 的線是「固定 v = offset」，沿 V 的線是「固定 u = offset」。因此兩條不同方向的線交點只需要兩行：u 取沿 V 那條的 offset，v 取沿 U 那條的 offset。

§5 · 完整角材實體

造出來、貼上去、再推導六個面

Timber 存三個尺寸，加上一個自己的框架（原點加三軸）。placed 旗標告訴你框架是否有效：剛 construct 出來時是標準框架，貼到表面後才換成真的。

整段最值得細讀的是 timber_place_a0_on_surface，它做四件事：長度軸取表面的 ±U 或 ±V；B 軸取表面法線的正或負；A 軸用叉積算出來，不用你手填；最後檢查 A0 面是否在有效區域內：多邊形凹角與孔洞讓「兩角點在內」不再是充分條件，所以改用整個矩形的包含檢查；另外長度端面若正好貼到外輪廓邊，該邊必須是 FIXED——自由邊外側沒有實體可釘。

timber_get_face_room 也不再逐面列頂點：六個面由「法向軸 k + 哪一側 s」一條規則推導——面內兩軸恆為 (k+1)%3、(k+2)%3，同一個繞行順序在 s=1 給 +k 法向、s=0 反走給 −k 法向，法向一律朝外。

§6 · 輸出函式

輸出不算幾何，只呼叫 get 再 printf

這一整段沒有任何幾何計算。每個 print 函式都是「呼叫上面的 get 函式、拿到結果、printf」。這就是輸出跟模型分離：想換輸出格式，模型一行都不用動。下一段的 SVG 輸出正是靠這一點才能純新增。

§7 · SVG 三視圖輸出

把 printf 的目標從文字換成 SVG 標籤

純 C 沒有畫圖能力，但 SVG 是純文字，所以「畫圖」就是 fprintf 一堆標籤。這段結構刻意跟 §6 平行。讀它抓三個關鍵：視圖框架、距離、兩趟走訪。

視圖框架：每個視圖是兩個互相垂直的單位軸：畫面向右 right、畫面向下 down。視線方向 into 不另外存，直接由 right × down 算出，跟表面的 U × V = N 是同一條公理。投影就是內積：畫面座標 = (p·right, p·down)。畫面方向與遠近順序出自同一組軸，所以畫面不可能是鏡像。

距離：點沿視線的分量 p·into 就是「離觀者多遠」。角材六個面在一個視圖裡只有兩個面有面積，其餘退化成線；有面積的面依距離由遠到近畫，最近的那面才標名。所以仰視圖標 A0（貼著天花板面、最靠近往上看的人）、前視圖標 B0、側視圖標 END。

後端介面：幾何層不知道自己在畫 SVG 還是視窗。它只呼叫 DrawTarget 裡的函式指標，說「畫一個多邊形，角色是表面」；長什麼樣子由後端決定。這是整段最關鍵的設計，§9 的視窗就是靠它接上去的。

兩趟走訪：scene_draw_view 的 target 傳 NULL 時只累積邊界、不輸出。scene_compute_layout 先用 NULL 跑三次量出每個視圖多大，排好版面算出平移量；之後 scene_render 再用真的後端跑三次。同一段畫圖程式碼不用寫兩份，而且 SVG 與視窗共用同一個版面。（函式開頭另有一條捷徑：世界沒有承載面時不量測，直接回一個最小空版面。）

§8 · 主程式

資料流的逐字翻譯，加一座實驗台

main 就是 §0 那條資料流一步一步寫下來，每一步失敗就印錯誤、回傳 1。下面只節錄放置角材與輸出 SVG 兩段。

放置實驗台

這座實驗台用 JavaScript 重寫了 timber_place_a0_on_surface 與三視圖的「最近面」判斷，邏輯逐行對應 C。改參數，看程式會接受還是拒絕、角材落在哪裡、每個視圖標哪個面。

三個建議實驗

1. 把 max_u 改成 2000

角材長 1800 從 u = 500 起算會到 2300，超出表面。放置那步應該拒絕：對角點 (2300, 327) 超出 max_u，整個 A0 面就不在表面內。

2. 長度方向改成 POS_V

看 A 軸怎麼被叉積自動算出來：Z × Y = (−1, 0, 0)。角材在仰視圖轉了 90 度，從 v = 300 往 +Y 延伸到 2100，寬度往 −X 佔 473 到 500。

3. B 尺寸改成 NEGATIVE

角材掉到天花板下方，Z 變成 2467 到 2500。仰視圖最近的面從 A0 換成 A1，因為往上看的人現在先看到比較低的 A1。

§9 · 第二層：作業系統視窗

不裝任何庫，只靠 Windows 自帶的 user32 與 gdi32

C 標準庫碰不到螢幕，螢幕是作業系統的財產。所以「不靠庫開視窗」最誠實的做法是直接呼叫作業系統：Windows 上就是 windows.h，每台機器都有，MSVC 也附帶標頭檔。所有 GUI 庫最底下都在做同一件事。這一段用 #ifdef _WIN32 包起來，其他平台編譯時整段消失。

讀它抓三個觀念，換成任何 GUI 庫都一樣：事件迴圈、回呼函式、只在 WM_PAINT 裡畫。

這一層也是「語言為體、GUI 為殼」的落點：視窗下方的輸入列收下的一行指令，交給的是與場景檔同一個 apply_scene_line()；滑鼠拖曳參考線，實際執行的是 guide_line_move() 這個 domain 動詞。UI 從頭到尾沒有直接寫過 World 的任何欄位——它能做的，不會超過 DSL 能說的。

效能實測（--bench 2000）：每幀重建所有 GDI 物件約 3.8ms，快取重用約 2.5ms——省三分之一。大頭不是位圖，是每個圖元的 CreatePen/CreateSolidBrush/CreateFontW。快取只住在 UI 層（GdiApp），domain 一行沒動。
代價：GDI 只有 2D，沒有半透明，只在 Windows 上跑。要 3D 互動或跨平台，第三層的 raylib 是最短的路，它本身也是純 C。但幾何層與 DrawTarget 介面不用改，再寫一個後端就好。
§10 · 場景檔：組成抽到程式外

七個指令的文字檔，就是這個 domain 目前全部能說的話

前面所有範例的結構都寫死在 main 裡。這一層把它抽出去：--scene 接一份文字檔，一行一個指令，由上而下套用——surface、edge、guide、timber、place，外加兩個狀態動詞 reset（清空重來）與 move（移動既有參考線）。場景檔寫不出第八種行為，也寫不出非單位軸的向量（軸只有 ±x ±y ±z 六個詞）；「封閉行為集合」在這裡是字面的事實。

邊界面可以有好幾片：surface 寫幾次就有幾片（上限 8），牆、地板、天花板各是一片，直立角材就是「貼在直立的面上」。place 因此必須明寫 on 面id——貼在哪片不再是隱含的。邊、參考線、錨點都各自記著 surface_id，誰屬於誰是資料裡的事實，不是靠順序猜。

id 要先宣告才能被引用，所以「place 寫在 timber 前面」自然變成「id 不存在」，不必另外規定。錯誤不直接印 stderr，而是寫進 domain 層的錯誤緩衝，檔案路徑與視窗輸入列讀的是同一份——拒絕的理由到哪一層都是同一個字串。合法的場景檔與 main 裡硬編的走同一個 World，輸出層完全不分來源。同目錄的 room_a.scene 是與內建預設等價的範例——兩條路徑產生逐位相同的 SVG。

move 有一條已拍板的語義：移動參考線不會讓已經放上去的角材跟著走。錨點是放置當下交出來的座標，不是對參考線的永久繫結——參考線只定位，不追蹤。

設計上最重要的一行註解：「軸只有六種寫法，所以場景檔根本寫不出非單位、非軸向的向量。」錯誤的輸入不是被檢查出來，是構造不出來——這就是公理作為根源的意思。
§11 · 數學：公式與隱形的矩陣

程式裡沒有 matrix 型別，但有三個隱形矩陣

這份程式刻意不寫矩陣型別——整數幾何下每個「矩陣乘法」都攤開成分量相加，效果相同、可逐行審查。但它確實用了三個矩陣，只是它們活在結構的欄位裡：

矩陣一：座標變換 M = [ U | V | N ]（3×3）

SurfaceFrame 的三個軸擺成直欄就是一個 3×3 矩陣。surface_point_to_room 做的事字面上就是仿射變換：

room = M · (u, v, w)ᵀ + origin = origin + u·U + v·V + w·N

角材的框架是同一個矩陣（timber_local_to_room 完全同構）。「框架合法」=M 是正交矩陣且右手向：surface_frame_is_valid 檢查的 |U|=|V|=1、U⊥V、U×V=N，正是正交矩陣的定義。軸只能是 ±X/±Y/±Z 六種單位向量，所以 M 實際上是「24 種軸對齊旋轉」之一——任意旋轉在這個 domain 裡構造不出來。

矩陣二：正交投影 P = [ right ; down ]（2×3）

ViewFrame 的兩個方向向量擺成橫列就是投影矩陣。view_project 是兩次點積：

view = P · p → x = p·right, y = p·down

三視圖 = 三個不同的 P（前視 X/Z、側視 Y/Z、仰視 X/Y）。這是丟掉深度的正交投影——丟掉的那個方向 into = right × down 沒有浪費，正好拿來畫遠近排序。

矩陣三：反解 A = P · [ U | V ]（2×2）

滑鼠反向查詢要把視圖座標解回表面 (u,v)：兩個未知數、兩條方程式。實際動手解的是 view_unproject_on_surface_near——裡面的 a, b, c, d 不是憑空的，它們是「先變換再投影」的複合，也就是 P 乘上 M 的前兩欄：

A = [ U·right V·right ] det = a·d − b·c [ U·down V·down ] u = (e·d − b·f) / det v = (a·f − e·c) / det （Cramer 法則）

同一個反解拆成兩版。_near 是容差版，給畫布滑鼠用：Cramer 的商用 llround 四捨五入到最近的整數 mm，滑鼠不必剛好落在整數點上；det = 0 仍是表面在此視圖退化成一條線，無解。嚴格版 view_unproject_on_surface 先借 near 解出候選 (u,v)，再代回原方程式驗算——答案必須讓 a·u + b·v 恰好等於 e，差 1mm 都拒絕。整數 domain 的「不猜」一路守到反解，只是守的方式從整除檢查換成代回驗算。
