## 已確認問題

### 1. [P1] 組構預覽漏掉外部依賴，確認卻提交其幾何變更

位置：`geometry-web/assembly_bridge.inc:32–38`、`geometry-web/assembly-workspace.js:187–231`。依據：公理 I8a 要求受影響角材的遞移閉包及新舊幾何。

重現：生成截面 27×33 的三構件實例，主支為角材 #1／#2；另外放普通副支 #92，以 `between t1 t2` 引用這兩支主支。把組構綁定 A 從 27 改成 40，預覽 `valid:true`，只列 #1／#2／#3。確認後，未列出的 #92 長度 **1973→1960 mm**，世界原點 x **514→520 mm**。

核心重算正確，預覽階段也沒有改 World；錯在必要的確認資料不完整。專用 serializer 只輸出規則、綁定和實例，前端因此只能呈現這些物件。

應收斂：由已完成全量重算的候選世界提供完整影響資料，讓組構、工程規格與一般引用入口沿用同一份幾何影響表示。保留各操作自己的輸入契約，移除各入口自行挑選下游幾何的責任。**不需要新增第二套角材求值。**

完成證據：上述 #92 在確認前必須出現在預覽；取消、過期與違規候選仍不改 World，確認仍只提交已看過的候選。

### 2. [P2] 匯入關聯使用另一套場景解析，會誤拒合法專案或漏掉無效附件關聯

位置：`geometry-web/reference-workspace.js:884–895`；對照 `geometry-web/project-store.js:51–66`。參考契約：`geometry-web/docs/REFERENCE-PROJECT.md` 的完整來源恢復與匯入驗證。

兩個反例使用真封裝、解包、工作區與隔離原生 bridge：

- 合法縮排 `  boundary 1 …`：核心建立面 1，前端卻報「來源關聯的面不存在於場景」，開啟失敗。
- `boundary 1 …` 後接 `delete boundary 1`，附件仍關聯面 1：核心最終沒有面，前端卻接受並替換專案上下文。同步物件後關聯消失，下一次匯出包的 `sources=0`。

根因是用「曾出現的未縮排宣告」代替「候選世界最後存在的物件」。另一份前端 parser 已處理 trim／reset／delete，兩者仍可能繼續分歧。

應收斂：在提交前，以原生候選的最終物件清單核對附件、投影及其他 metadata 引用；移除匯入流程這份宣告掃描。單純在第 884 行補一個 trim，仍會留下 delete／reset 的分歧。

完成證據：合法縮排可開啟；不存在的目標關聯在替換目前專案前被拒絕。核對來源 bytes、關聯、World 與復原單位，而不只看檔案雜湊。

驗證範圍：圖片解碼與 HTTP 使用 VM 替身，`loadfile/dump/objects` 來自新編的隔離原生 bridge。已證實新匯出包遺失附件，**沒有刪除原檔，也不代表一般 UI 保存必然觸發此問題**。

### 3. [P2] 來源定位丟失承載面身分，同一邊界多次放置時會找錯工作區

位置：`geometry-web/source-inspector-app.js:24–30`；對照 `geometry-web/engineering-adapter.js:98–113`、`geometry-web/app.js:2835–2840`。

前提由新編 bridge 確認合法：同一 boundary 1 可被 placement 10、20 引用，角材 #7 放在 20。來源圖保留 `timber:7 → placement:20 → boundary:1`。

來源定位卻只用 boundary 1 進入面工作區，沒有傳 placement 20；`feSurf()` 隨後取第一個 placement 10。隔離執行正式導航程式，在「從畫布進入」及「已開著 placement 10」兩個情境，都得到工作區 10、沒有選到 #7。

工程規格入口已傳遞 `placementId` 並核對目標；來源定位入口尚未沿用相同身分處理。相近的定位責任目前在兩條路徑分別維護。

應收斂：共用一個按原生物件身分定位的面工作區入口，保留 boundary 與 placement，核對已開啟工作區及目標物件。不從顯示名稱或第一個匹配項猜位置。

完成證據：兩種進入情境都開到 placement 20 並選中 #7；定位不改 World 或歷史。VM 已重現導航缺口，尚未做真瀏覽器端到端驗證。

### 4. [P2] 閱讀器補丁登記有提前返回，保護機制本身漏檢

位置：`geometry-guide/sync_axiom_reader.py:786–799`；對照 `tests/test_axiom_reader.py:270`。

`force(..., marker=...)` 在 790／794 行返回，沒有進入其後的補丁登記。目前有四個呼叫走這條路徑。隔離呼叫得到 `new MARK`，登記數仍為 0；再刪掉 marker，`PATCHES.verify()` 仍沒有報錯。

總登記量 99 大於測試門檻，不足以證明每個補丁都已登記。這與 AGENTS 的明確紀律不符。

應收斂：讓所有分支在返回前完成同一份登記；以單次呼叫的登記和「標記消失必拒絕」核對 helper。沒有證據顯示現行四個 UI 行為已壞掉，問題是失效時可能無法被攔住。

### 5. [P3] 已完成的閱讀器 UI 遷移仍留在每次重建，且舊實作沒有退出

位置：`geometry-guide/公理層-閱讀器.html:3654`、`:3677`；同步器 `:899`。

正典保留兩份 `renderWitness`，在 3669、3694 行各註冊一次 `axiom:current`。JavaScript 的後一份函式覆蓋前一份，兩個 handler 都呼叫新版；這是死碼與重複工作，並非兩套活動求值器。隔離執行原碼，一次事件複製 SVG 兩次，最後仍只有一張圖；尚未量測真瀏覽器可感知的效能影響。

同一次記憶體重建，46 次 `force()` 全部沒有改動文字，卻繼續約束現行 HTML。只替 `function reanchor(c){` 加一個空白，完整性驗證仍通過，重建卻因 Python 裡的整段字串不匹配而拒絕。維護 UI 時因此要理解現行功能與歷史改寫條件。

應收斂：先移除重複見證圖實作，再逐項將已完成的 UI 遷移退出常態資料同步。保留 Markdown 解析、段落身份、批註保全、JSON／DOM 一致性、圖及追溯資料嵌入。**46 次無改動不等於可以直接刪除全部 46 項**，要核對各項用途與相容需求。

完成證據：單次事件只有一個見證圖更新；目前 UI 有清楚的修改位置，正常更新不需同時維護已退役的 OLD／NEW 片段。仍只有既有正典閱讀器，保留單檔離線、批註及五道 assert。

### 6. [P3] 閱讀器顯示過期條文總數，既有計數檢查沒有涵蓋它

位置：`geometry-guide/sync_axiom_reader.py:891`、`geometry-guide/公理層-閱讀器.html:136`。

無見證圖的側欄寫「89 條中有 31 條有」，目前 `clause-data` 實為 118 條。`--check` 與 25 項閱讀器測試均通過。

應收斂：總數直接來自目前條文資料，該顯示欄位納入資料一致性檢查。繼續增加過期數字黑名單，無法移除第二份計數真相。
