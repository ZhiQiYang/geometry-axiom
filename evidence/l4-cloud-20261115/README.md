秒數是不開統計的那一趟；次數是另一趟用瀏覽器的函式呼叫統計數的（開統計時較慢，兩趟的數字分開記在結果檔）。只在這台容器量，各量一次。

**原因**（`geometry-web/project-store.js`、`feature-attachments.js`，這張 PR 先前沒有改過這兩個檔）：三層重複互相相乘。`projectFormat` 每判斷一種格式就重算一次需要的能力（有規則案例時 7 次）；`projectCapabilities` 對方案目錄裡的每個方案，在六個判斷裡各重算一次；`Features.validate` 在同一次呼叫裡連續三次遇到同一份案例資料，每次都跑完整的案例檢查。節點測試直接數一次 `projectFormat` 的整份檢查次數（`scripts/count_validations.js`，`d15/save-timing/validation-counts.txt`），方案數 0／1／2／4：main 與修正前都是 21／147／273／525，修正後（`b5195a5b`）是 1／2／3／5。

**修正**（同一張 PR；結果不變，只少做重複的工作，不放寬任何檢查）：

- `project-store.js`：最外層的一次同步呼叫開始時建立一份記錄（以 manifest 物件與場景文字為鍵），同一次呼叫內再問到同一份的能力就回已算過的結果（每次回一份新的陣列），呼叫返回或丟出例外時清掉；不跨呼叫保留。原本的計算整段搬到 `requiredCapabilities` 之下，內容不變；和修正前相比這個檔只多 13 行，原有的每一行都沒有改。
- `feature-attachments.js`：一次檢查呼叫內，同一份案例資料只跑一次完整檢查並記下位元組數。記錄隨那一次呼叫結束，不跨呼叫保留。
- `rule-case-data.js`：計算 UTF-8 長度不再為每個字串配置位元組陣列，數值與 `TextEncoder` 相同。

**結果有沒有變**：

- 新舊實作對照（`scripts/differential_project_store.js`，舊 = `2a62073f` 的檔案、新 = `b5195a5b`）：倉庫裡 191 個 `.gcanvas` 加上修正後正式關卡產生的 2 個（含規則案例與方案目錄），逐檔比較解包、格式判斷（含清掉宣告能力後的最低格式）、驗證、附件驗證、附件能力、重新打包後的 manifest。193 個全部相同，其中 6 個新舊都拒絕（`d15/save-timing/differential.result.json`）。
- `tests/test_rule_case_project_store.js` 加 3 條（`node:tests-js` 780 → 783）：判斷格式時每份附件只檢查一次（方案數 0、1、4）；不保留上一次的結論（通過之後才被改壞、一開始就壞、放在第二個方案裡的壞資料都照樣被拒）；位元組數等於實際 UTF-8 JSON 大小、名稱上限 96 位元組在 1～4 位元組字元下的邊界都正確。反向對照：還原 `project-store.js` 或 `feature-attachments.js`，第一條失敗；把長度算錯兩種方式，第三條失敗。

**沿革**：第一版修正（`cdb00462`，包含在 `d7f79eab` 裡）把 `projectFormat` 與 `projectCapabilities` 裡重複的呼叫改寫成先算一次再共用。那一版的正式關卡同樣 76 項通過，但改到的那幾行被幾組突變定義用逐字比對來定位，CI 的 browser-mutations 在 head `7c360714` 失敗（`anchor occurs 0 times`，兩筆 R06 突變）；推送前沒有跑那個檢查器。`b5195a5b` 改成上面的做法，那些行一行都不動，突變定義沒有改。上表與上面的對照都是在 `b5195a5b` 重跑的；`d7f79eab` 那一版的收據沒有留在資料夾裡（在 git 歷史 `4f23e777`）。

沒核對的：很大的專案（大量房間來源、證據、模型）保存方案的時間沒有量；修正後同一次保存裡仍有 84 次整份檢查（來自不同的呼叫點），這次沒有再動。R06 突變檢查器的節點與瀏覽器執行在這台容器跑不起來（既有環境問題），兩筆突變是手動套用確認仍然生效的，正式結果以 CI 的 browser-mutations 為準。

另外兩點不算缺陷：
