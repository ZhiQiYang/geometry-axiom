# 五項 browser 外部調度器獨立靜態審查

結論：目前沒有阻擋採用的靜態問題。這份結論只涵蓋外部調度與判定器，不是五項 browser 的執行通過聲明；尚未獲 L SHA 與排程放行前不得啟動。

定版工具：`run_browser_five.py`，SHA-256 `4ffefe74d503506f2c99d3064fac4359c4aa5324f77ccf5e3ae44bdf6ec994f2`。審查時主樹為 `7159530c0e494d3211e6ab1764eb691137211707`。審查者沒有改主樹，也沒有為此啟動 build、服務或 browser。

- 每項 job 由建置前啟動單一 monotonic deadline，限額沿 workflow；所有 browser 步驟只取剩餘預算，預留 15 秒清理。產物複製、雜湊與最終收據亦列入期限判定；超時不留成功狀態。
- 完整 40 位 SHA、明示 execute、放行說明、乾淨工作樹及輸出不覆寫皆在啟動前守門。fresh probe 核對 root、來源版本與自有 server PID，結束再核同一 runtime、HEAD、工作樹與來源 hash。
- 每項服務與 browser 使用獨立埠及 TEMP/profile/feedback。build/server 的 TEMP 固定 /tmp，node 的 TEMP 為本輪子目錄；feedback 同時符合兩者路徑契約。documents 忽略 profile 覆寫的實況有註明，以專屬 TMPDIR 隔離。
- Linux subreaper 只接回自身後代；記錄 PID/startTime，訊號用 pidfd 解除核對後 PID 重用競態。僅清自有程序，未用全域 pkill/killall。結尾以 connect_ex 必須 ECONNREFUSED 配合自有程序退出，避免 TIME_WAIT 的 bind 假紅。
- 清理、產物封存、來源核對與雜湊各自捕捉錯誤並保留收據。原 browser exit 與外層 validation 分列，缺結果、截斷、partial scope 不符、期限到達均不會算通過。
- assembly/grid 使用原 harness 原有 partial scope，外層核所選段完整 census；沒有拿它們冒充完整 canvas golden。兩套 scope 未包含 P38，例外數要求 0 合理；完整 canvas 的預期 fb-auto-probe 另由 canvas 調度器核對。
- documents 從固定來源獨立盤點 47 個依序具名 check，實際 PASS 名稱及順序須完全相符，不能只用非零總數與最後兩題判完整。逐讀目前來源，check 沒有條件分支或迴圈生成；來源改變須重新盤點，這不是一般 JavaScript AST 分析器。
- space/timber 同時核 SPACE_RESULT 與落地 result.json，固定每群題數、群集合、completed、健康守門與每個明細 ok，保留既有 included 範圍。
- 字型套件必備，保存預設 sans 實際匹配，另驗 Noto CJK 可用；不把 OpenAI Sans 首選誤判成缺中文字型。原生 binary 的既有 fingerprint sidecar 與實際 bytes/hash 一併封存。
- 預期截圖名稱已逐項對照現有測試呼叫，且每輪專有輸出/TEMP 消除舊圖混入；PNG 檔頭檢查只能證明基本檔案格式，視覺品質仍須另讀圖。

原審查指出的 bind 清理假紅、收尾未完整計時、finally 錯誤可能遺失收據、documents 中段完整性不足均已修正。AST/hash 輕量命令最後重跑 exit 0；預期截圖來源 rg 核對 exit 0；documents 具名盤點為 47。中途曾遇 exec-server 暫時斷線，之後正常重讀同一 hash，未以該次未知退出碼宣稱成功。

限制：這是靜態審查，還未實測各套原 browser、實際時限與清理。非正常作業系統 I/O 阻塞可能延長收尾；工具以最終 elapsed 決定不得超時通過。真正的 L 驗收必須保留每輪原 log、runtime、來源、native、截圖、退出及清理收據，不可由本審查取代。

## 持久化啟動器補審

`launch_browser_five.py` hash `479cdcd9f1c1c03ab203aff6fc5f0f9fddb3c70d779507777c7c1d903762f124` 無新增阻擋。它先核已審 wrapper hash，保存自身與 wrapper 原 bytes，直接執行同 bytes 文字快照；stdout/stderr 寫檔、stdin 為 DEVNULL、子程序獨立 session。取得真 wait() 返回碼後，第一個收尾動作以 flush/fsync 寫 `.exit-code`，之後才整理 JSON，不依賴工具 session 或產品 passed 欄位推造退出碼。SIGINT/TERM 只轉交仍歸本父程序持有的直接子程序，SIGHUP 忽略。

已只讀逐一核對三組假程序的 `.exit-code`、launcher receipt 與原 stdout：0、7、-15 完全相符；含 stdout 聲稱 passed=true 但真碼 7 的控制，沒有誤判為 0。-15 的 helper 對外規劃碼為 143，原 wait 碼仍為 -15，不能混稱產品失敗。兩項 CLI 拒絕均 exit 2、沒有啟動正式 wrapper。審查者另跑 AST/hash 與收據資料核對，均 exit 0；未重跑控制或啟 browser。
