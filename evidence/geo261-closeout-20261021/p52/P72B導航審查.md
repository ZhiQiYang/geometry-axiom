## 缺口及最小修正

`geometry-web/grid_inspector_rename_test.js` 原碼在 `Page.reload` 或 `Page.navigate` 回覆後，僅等待 `ReferenceWorkspace` 已定義、`connection.phase==='ready'` 及工作區非忙碌，隨即呼叫直接存取 `oc` 的 `settle()`。

這個條件沒有識別新舊 document。原頁本已就緒，導航命令回覆也不代表新頁腳本執行完畢；因此第一個等待可在舊頁滿足，接著 `settle()` 恰好於新頁 `app.js` 宣告 `oc` 前執行而丟錯。此可達時序符合 log，但原 log 沒有保存那次等待的逐次 evaluate 回覆，尚不能聲稱已直接觀測到當時舊頁回傳 true。

`p72-navigation-candidate.patch` 只修改這個模組的導航同步：

1. 新增模組內 `navigate()`，每次導航前用 `Page.addScriptToEvaluateOnNewDocument` 登記唯一 UUID 標記。
2. 導航命令回覆後復用既有、未修改的 `cdp_navigation.js::waitForExpectedNavigation`，要求本次標記、新頁 `document.readyState==='complete'`、應用物件存在、連線就緒及工作區非忙碌；此等待維持原有 20000ms 預算。這是就緒等待期限，外層 `Page.reload`／`Page.navigate` 與標記清理仍採原 CDP send 的 120 秒期限，不稱為整個 navigate 的 20 秒總期限。
3. 在 `finally` 移除新頁注入腳本，避免污染後續導航。若導航與清理同時失敗，以 AggregateError 保留兩個原錯誤及訊息；不能只留下清理失敗而遮蔽原始根因。
4. 開檔前重載、第二服務開檔前，以及第二服務完成後返回原服務，均走同一等待。

原 `settle()`、所有幾何／來源／保存／引用比較及 50 個 P72B 斷言均未修改；既有 golden、產品來源、公理與 P-177 流量均未修改。沒有把一般 evaluate 改成吞錯重試；既有導航 helper 只重試三種精確的 CDP context teardown 錯誤，其他腳本／協定／超時錯誤仍立即失敗。

## 完整 50 題的最快執行方式

`p72_probe.cjs` 擷取指定工作樹原有的 CDP 啟動器，然後直接執行完整 `grid_inspector_rename_test.js`；保留真實輸入、原模組的保存／重開流程及全數 50 題，不跑前段 P1–P72。它是局部驗收工具，不能替代正式完整 canvas。

以下示例假設主代理已釋放獨占量測資源、`18839` 是本次隔離服務且沒有另一個 canvas 使用該服務。執行前要核對實際 URL、feedback 目錄及空閒 CDP port；不得指向使用者專案服務。

```sh
GEOMETRY_TEST_URL=http://127.0.0.1:18839/ \
GEOMETRY_FEEDBACK_DIR=/tmp/geo261-feedback-final \
GEOMETRY_CHROME=/usr/bin/chromium \
GEOMETRY_CHROME_FLAGS=--no-sandbox \
GEOMETRY_CDP_PORT=9351 \
node /workspace/geo261-evidence/p52/p72_probe.cjs /workspace/geometry-axiom
```

真實來源尚未修正時，追加 `P72B_CANDIDATE_NAVIGATION=1` 才是在記憶體安裝候選；來源已套候選時直接使用預設命令。工具只檢查原版／候選導航片段的唯一性，並非整檔白名單；須用記錄的實際 SHA、git 狀態、實際／有效模組與 harness 雜湊、工具雜湊及 `memoryPatch` 對照受審來源，不得僅因片段相符就宣稱整檔已審，也不得將記憶體安裝候選的結果稱為該 SHA 的原版結果。

若驗第二個獨立 native process，正常 50 題命令另加 `GEOMETRY_GRID_RENAME_FRESH_URL`。該模式保留原模組對第二服務 root、version、fresh、PID 與 session 的斷言。導航注入模式限定同服務 reload，與第二服務驗收分開執行。

## 真瀏覽器負控制設計與預期

目前只有設計、靜態審查與語法結果；以下各項尚未實跑，不能預先列為通過。

### 受控舊頁先滿足：`P72B_NAV_CONTROL=stale-first`

不是偽造 `Page.reload` 回覆或 evaluate 布林值。工具會透過真正 CDP Fetch：

1. 在 P72B 開檔前的真實 reload 暫停新 `Document` 請求，保留已就緒的原 document。
2. 對原等待或候選等待執行真實瀏覽器 evaluate，記錄它回傳的原值、舊頁 readyState、`typeof oc` 與連線狀態；必須確認舊頁 complete、oc 為 object、連線 ready，且原版實際回傳 true／候選實際回傳 false，否則視為控制設置失敗。
3. 釋放 Document，暫停新頁真正的 `app.js` 請求；另外以只用於控制收據的 UUID 確認已換成新頁，且 readyState 尚未 complete、`typeof oc==='undefined'`。
4. 將第 2 步的真實值原樣交回測試。原版等待會得到舊頁的 true，隨即在新頁呼叫 `settle()`；候選應得到 false，再等新頁標記、complete 與連線就緒。
5. 1200ms 後放行 app.js。候選應完成原 50 題；原版或精確撤回等待應在第 46 題後、原 `settle()` 讀 `oc` 時明確紅燈。

每個控制步驟都會輸出 `P72B_NAV_CONTROL` 收據；若無法建立「本次新頁但 oc 未宣告」的條件，工具直接紅燈，不把控制設置失敗當成已重現原缺陷。

建議順序：

| 真實來源／追加環境 | 預期 | 可宣稱內容 |
|---|---|---|
| 已修來源，無注入 | exit 0、50 題、0 例外 | 正常 P72B 驗收 |
| 已修來源，`P72B_NAV_CONTROL=stale-first` | exit 0、50 題、0 例外 | 候選能等到正確新頁 |
| 已修來源，`P72B_WITHDRAW_NAVIGATION=1 P72B_NAV_CONTROL=stale-first` | exit 1，46 題後 `oc is not defined` | 精確撤回轉紅；須核對錯誤及控制收據，不能只看 exit 1 |
| 未修來源，`P72B_NAV_CONTROL=stale-first` | 同上紅燈 | 原版故障注入；不能稱為撤回自證 |
| 未修來源，`P72B_CANDIDATE_NAVIGATION=1 P72B_NAV_CONTROL=stale-first` | exit 0、50 題 | 記憶體候選控制；不能稱為原 SHA 原版通過 |

### 文件始終未替換：`P72B_NAV_CONTROL=hold-document`

僅接受有效候選來源。真正的 reload Document 請求持續被暫停，舊頁仍維持 ready；候選必須約 20000ms 後以導航等待逾時明確紅燈，不能因舊頁已 ready 而進入後續四題。工具不改 helper timeout，也不偽造 evaluate 回傳。Browser 關閉後暫停請求一併終止。

### 例外與清理邊界

工具沿用原 harness 的 `Runtime.exceptionThrown` 計數。任何未完成、斷言數非 50、失敗斷言或瀏覽器例外均不能 exit 0。來源尚未修正時禁止 `P72B_WITHDRAW_NAVIGATION=1`。清理先送 Browser.close，必要時只終止本工具自己建立的 Chromium child PID，不廣殺其他瀏覽器；SIGKILL 後再有界等 1 秒，依 exitCode 或 signalCode 確認退出，若仍未退出即明示清理失敗。工具專用的 `__p72ProbeDocumentMarker` 注入腳本及 Fetch 攔截隨此專用瀏覽器關閉清除，不會用在下一次共用瀏覽器執行。
