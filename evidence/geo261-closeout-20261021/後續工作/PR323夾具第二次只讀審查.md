## 同一生命期的必要條件

1. `reference_member_anchor_read` 的 id guard 在 `geometry-app/native/reference_sources.inc:506`。差異需要同一快取索引 i 已存 id A，之後在未清除快取的情況要求 id B。
2. 同檔 `:515` 的 `footprint_valid=false` 只有在 anchor miss 且實際來源讀取成功後執行。要殺掉此句，必須先自然填入 footprint，再使同一 i 的 anchor 讀取走 miss，且後續真的使用舊 footprint。僅「曾讀過 anchor」不夠。
3. 同檔 `:618` 的 placement guard 位於 `:616` 的「actual anchor 宿主等於 request 宿主」檢查之後。footprint 只在 `:638–640` 存入當次 request 宿主；同一 id 的 anchor 命中保持原值，換 id 又在 `:515` 先清掉 footprint。因而兩個宿主、不同查詢順序，尚不足以單獨讓 placement guard 有差異。

這是針對已讀呼叫鏈的局部條件分析。未證明所有可能 callback／重入／來源失敗恢復的全域不變量，因此不作全域等價宣告。

## 對夾具設計的具體修正建議

- 將前兩項「公共測試 consumer 包住 helper」明確標為 **helper 的索引／身分防禦控制**。外層用 `geo_eval_register/geo_eval_source` 不會自動使內層 `reference_member_anchor_read(ctx, indexA, idB)` 變成正常 H adapter 序列。使用真實來源資料比手填 cache 好，但仍缺產品呼叫端的可達性證據。
- footprint 暖快取必須經真正 `reference_contact_facts`／contact collect。一般 `reference_member_footprint`（`reference_sources.inc:517–532`）會算矩形，卻不寫 `member_reads[i].footprint_valid`；不能把「先叫公開 footprint 包裝」當成 cache 已暖。
- 對移除 `:515` 失效句的控制，先要求可觀察的錯誤矩形或完整來源圖差異，再稱 killed。暖 A→以人工 alias 讀 B→再回 A 會再次變成 anchor miss；即使失效句刪除，舊 A footprint 也可能剛好仍正確。只看私有旗標不是產品幾何 oracle。
- placement guard 的單點突變不可由「兩宿主都查得到」推定被覆蓋。應先觀察到「footprint_valid=true 且 cache.placement != request.placement，但前方 actual-anchor 宿主檢查通過」這個分岔前提。未觀察到前維持未證。
- 暫不靠同時移除 id guard／失效句去製造單一 placement guard 的 kill；這會改成不同突變命題。若另設組合控制，必須獨立列名與裁判，不能回填成單點突變成績。

## 已有較強產品路徑，不應被前三項的不確定拖住

pose relation 與依賴記錄有可具體化的正常序列：

- A 先放、B 後放，B 以 timber／between 明確引用 A 且同宿主。W 在 `member_reference.c:158–160` 先對 A 登記 `EVALUATE_BEFORE`，再在 `:168–172` 登記 `VALUE_REQUIRED`；H `reference_sources.inc:831–842` 的 cache hit 必須保留傳入 relation。
- 圖的 oracle 應比較有序的完整 consumer/source/provider/key bytes/kind。kernel `source.c:189–199` 按含 kind 的 edge 身分去重並保留插入順序；只查「有一條邊」會漏掉 kind 或順序錯誤。
- W collection→feature 的 cache-hit 依賴有正常入口：`contact_sources.c:177–185` 先求 collection，再逐一求 feature；此 PR 實際 dependency 行為是 `:127–136`，`geo_eval_depend` 在 **134**，應以此 SHA 的 anchor 調整舊行號。這個路徑無需假造 World 或私有 cache。

以上是來源推導，尚未建新夾具或執行突變，不能列為已通過。sealed contact helper 控制亦仍應與正常 `wood_contact_sources_collect` 分開：後者在 `contact_sources.c:170` 明確拒絕 sealed graph。

## 最有希望的下一步與停止條件

最值得先觀察的是「組件生成讀 guide／member，接著生成寫回，再進 reference_rebuild/contact」的同一生命期。這裡有真實內部寫回及遞迴求值，比一般跨指令移動更有機會揭露前提缺口。需在未改決策順序的觀察插樁中記錄 evaluation generation、slot、world id、cached id、anchor hit/miss、cached placement、request placement、footprint_valid、sealed，以及呼叫鏈。若仍只有同 id／同宿主，應停止宣稱這組場景可殺前三個 guard，保留未證；不要改測試使錯誤 alias 變成「正常產品輸入」。

其次可查 create/delete operation 是否存在合法的同 generation 重入。必要證據是從公開入口一路到已暖快取後的 allocate/remove，且中間沒有 dispose/reset；目前只有 callback 的存在，尚無這條實際呼叫鏈。直接讓測試沿舊 graph 改 World 違反本次限制。

最大不確定在於所有深層 callback／重入路徑未被動態列舉，以及組件／guide 的求值時點可能先暖某些 member cache。靜態檢查不足以排除全部可達性；但即使找到同 id 的 anchor 寫回，也必須再證明這三個特定 guard 會產生差異，不能把其他 stale-source 問題混入。
