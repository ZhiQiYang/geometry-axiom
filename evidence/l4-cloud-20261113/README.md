| 結果 | `walk_*.result.json`（腳本當下讀到的畫面文字與數字）、`screens/*.png`、保存出來的 `.gcanvas`、`scenes/`（產生的場景檔） |

點按、填寫、選擇、拖曳、右鍵都由 Playwright 對畫面元件送出真的滑鼠／鍵盤事件。`page.evaluate` 的用途與 11-07 相同，這次具體是：

1. **讀畫面**：狀態列、表單欄位、對話框文字、下拉選項。
2. **唯讀讀取 App 內部值**：`apiRequest('dump')`（場景文字，用來比對前後是否相同、數角材）、`apiRequest('panel-fill-read')`（唯讀，取完成面／鋪排／宿主的筆數與修訂號）、
   `feMmToPx` 與 `fevp`（把面內 mm 換成螢幕像素，之後用滑鼠點下去／按右鍵；R11）。
3. **以腳本代替介面操作**：`scripts/lib.js` 把 `showSaveFilePicker`／`showOpenFilePicker` 設成 `undefined`，讓 App 走下載與 `<input type=file>` 後備路徑（與 CI 相同）；
   `lib.js` 的 `trackApi` 只**旁聽** `/api` 的回覆（記錄指令與 ok／error），不改請求。
4. **指令列**：R04、R06 衍生面需要「放很多支角材」「在衍生宿主上放邊界角材與定位線」，經 App 的「進階指令」列（`#cmdToggle` 展開，輸入後 Enter）。
   這是 App 的真實入口，不是測試夾具；但一般使用者放角材的主要路徑是面內「角材」工具，這次沒有用它逐支放 110 支（見未核對）。

**界線：** 這是雲端實機操作，不是使用者驗收（L5）。沒有核對：Windows 本機、實體觸控、中文輸入法、原生檔案對話框；
**所有秒數都是這台雲端 Linux 容器的量測，不能直接當成使用者 Windows 機器上的數字。**

## 操作中發現的問題

6. **專案裡已有舊式（單一開間）組構實例時，重複開間預覽被前端擋下**（R06 衍生面核對時發現，**一般承載面也會發生**；編號接續 11-07 的 1～5）。
   重現：開啟 `geometry-web/examples/assembly-generation-v1.gcanvas`（含一個舊式實例 #1，角材 1、2、3）→ 照上面步驟設好重複開間 → 預覽變更 →
   狀態列「原生服務的所屬角材身分不完整；草稿仍保留。」，不能確認。原生預覽本身是有效的（`walk_r06d-nodelete.result.json` 的 `asmWire` 記下
   `/assembly/generate-preview` 的回覆：新增 4 支、舊實例的角材列為 `kept`）。
   原因：`geometry-web/assembly-workspace.js` `assertRepeatPreview()`（約 340–350 行）檢查每一列 `owner.identity`，
   只認 `primary`／`secondary` 兩種；舊式實例的角材身分是 `{"memberId":N}`（例如 `{"instance":1,"identity":{"memberId":1}}`），被判為「不完整」並取消預覽。
   11-07 的 R06 腳本與 `assembly_bay_repeat_test.js` 的 `fixture()`的 `fixture()` 都先把舊實例刪掉才建重複開間，所以沒有碰到。
   本次核對照 11-07 做法先刪舊實例；證據：`walk_r06d-nodelete.result.json`、`screens/R06d-nodelete-3/4/5-*`。
   修法建議：`assertRepeatPreview` 接受 `positiveId(identity.memberId)` 的舊式身分；另補一個「專案已有舊式實例時重複開間預覽仍可確認」的瀏覽器測試。
   這次**沒有改產品碼**（見 PR 說明）。
7. （觀察）`ASM_BAY_WORLD_MAX` 的拒絕理由在畫面上是 `CAPACITY · I33/I69 …` 的核心原文，不是白話文；#378 合併時可一併處理。
8. （觀察）超過上限的拒絕訊息「角材的數量超過上限」沒有寫出上限數字（512），使用者看不出離上限多遠。
