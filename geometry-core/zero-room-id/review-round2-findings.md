# K2b 第 2 輪審查要點（2026-10-10，opus；原樣照錄，修訂 agent 不得改寫本檔結論）

結論：須先改，沒有阻擋項。F1–F6 每項都只是改一句條文或一列契約，改完就可以寫入。
下文縮寫：rw = `geometry-web/reference-workspace.js`，rcw = `geometry-web/room-collection-workspace.js`。
程式行號以 `a7bff8f4c7a0d61a3133b6e42d0d513dfe96367e` 為準。

**F1 接受路徑與 S5 那一句互相矛盾**
- 原因：接受候選時，草稿與新的 D3、房間記錄是同一筆交易，所以「唯一變更」永遠不成立。這也和 R⟨K2b-2⟩ 的延續規則、以及 rcw:432–447 衝突。
- 裁決：
  - S5 那一句的適用範圍限定在「暫停、保存前同步、捨棄」三種情況。
  - 接受改用 R⟨K2b-2⟩ 加上現行回執來證明，並加一條「草稿等於同一群組剛寫入的值」。

**F2 /api 白名單漏列了幾處**
- 漏列的位置與用途：
  - `app.js:546`：沒有 requestId 就沒有回執，IM17 必定失敗。
  - rw:37 的 `nativePending`：讓 `assertSaveReady`（rw:1239）在確認進行中擋住保存。
  - `app.js:555`：確認租約。
  - `app.js:532`：可編輯性守門。
  - `app.js:608`：發出 `geometry-definition-changed`，讓 `parameters.js:921`、`assembly-workspace.js:326`、grid:1019 的預覽失效。
- 裁決：
  - 在 §2.3 和 §2.7 補齊以上各處。
  - 改寫 §3 和 §1.7：`app.js` 是必改的檔案；兩個 PR 的重疊範圍要照實寫。

**F3 I⟨K2b-5⟩ 寫「回覆未知……不改目標 World」**
- 問題：這和 IM17 互相矛盾。回覆遺失時，原生端可能已經提交了。
- 裁決：改成「回覆未知時不重送、不推定結果，以回執為準」。

**F4 保存時同步會跑兩次**
- 原因：rw:1516 先同步一次；:1530 設了 busy 之後呼叫 exportSnapshot，其中 :1258 又同步一次。而 setFeatureAttachment 會先檢查 busy 就丟錯（:483），「值相同就直接回傳」（:486）排在後面。
- 裁決：
  - 同步前先用快取值自己比對，或在 busy 時跳過。
  - PC17 改成「第二次是無操作、不報錯、不出提示」。
  - 更正 AXIOM-DIFF §6 的自查內容。

**F5 值沒變時，字面會被讀成要退休**
- 裁決：補一句「沒有寫入就不重新蓋章，工作階段維持不變」。

**F6 條文用了未定義的詞，並和契約自相矛盾**
- 問題：I⟨K2b-3⟩ 說新鮮度只看領域指紋，但契約依賴 candidateStamp（含 revision 與 undo 頂端，rw:148–150、rcw:150–155）。另外「工作階段」「重新蓋章」在公理層沒有 D 編號。
- 裁決：
  - 條文明確分開兩件事：「草稿新鮮度」用領域指紋，寫在公理層；「本分頁工作階段有效性」屬實作契約，不寫進公理層。
  - 把「工作階段」「重新蓋章」移出公理層。
  - 定好工作階段失效而不寫入時要給的提示，並加一條 PC。
