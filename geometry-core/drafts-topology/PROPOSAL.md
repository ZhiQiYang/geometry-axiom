# A 部：#45 多份網格草稿

## A1. 問題

`grid-draft` 附件每專案 0 或 1 份（`FEATURE-ATTACHMENTS.md`）。使用者填網格來源 X（例如 step 打成 `1e`）到一半，想先改配置 Y，介面跳出
`grid-system-workspace.js:948`「專案已保留一份原始網格草稿。改開另一個來源／配置將取代它……確定取代？」——只能放棄 X 的輸入，或不能動 Y。

## A2. 行為與依據

1. **同一已提交目標至多一份非孤兒編輯草稿；開啟編輯即續開那份。【選擇·UI 減項】** 網格工作區只有單一編輯窗，續開能省掉「多份裡挑哪份」的明選步驟。
   這**不是**定義推論：組構實例的編輯同樣是原位取代（`edit-instance`＋expectedFingerprint），現行卻允許同一實例多份草稿、由清單明選，行為也唯一。所以本限制只套網格草稿，組構草稿照其契約可多份。
2. **新建草稿可多份。** 正式 id 在確認時由核心配發，不預留（沿現行 grid 草稿與 Q36b），多份新建不撞號。
3. **草稿不可互相引用。【推論】** 公理已有 I8a `:602`、D26 `:360`、D32 `:483`。配置草稿要用的新來源必須先提交。
4. **孤兒永不復活；來源引用也是曾經缺失即永久。** 原生 `newid` 以「現有最大 id＋1」配號（`web_bridge.c:391-407` 的 `WORLD_NEXT_ID`，`:484-491` 配系統、配置、參數卡），刪掉最大的系統 2 後，下一個新建又拿到 2。
   來源引用的 pin 只比對 id 加內容指紋（`grid-system-workspace.js:26` 的 `pinKey`、`:27` 的 `samePin`、`:30-36` 的 `catalogPins`）。只比 id＋指紋，舊草稿或舊引用會對上新物件；內容剛好相同時甚至會通過 pin（違反 D30「不以編號猜身分」）。
   所以：本專案中任何一筆已提交的交易，只要其任何操作使基底不存在（提交中任何操作使物件不存在，即為明示刪除），或結果中基底不存在，該草稿就**永久**標成孤兒（同一歷史步驟寫入）。判定依據是「本專案提交紀錄中觀察到的基底缺失」，不是 id＋指紋。孤兒不算同一目標、不佔名額、只能保留或捨棄。
   同一條「曾經缺失 → 永久」擴大到每一個來源引用。**這是逐引用的旗標，不是第四種草稿狀態**：草稿狀態仍只有有效／過期／孤兒，`lost` 與狀態並行。每個來源引用（`inputRefs` 項目）帶 `lost:true` 欄位；該引用的對象一旦在提交紀錄中被觀察到缺失（任何操作使它不存在，或結果中它不存在），旗標即永久為 true，隨集合格式保存（A4），不論草稿本身是有效、過期或孤兒。缺失過的引用只能明選另一個物件來替換，不能用同一個 id 重新取得；參數卡 id 同樣不能重新取得。**任一引用 `lost` 的草稿不得預覽或提交，不論其狀態。**
   前端歷史上限 32 筆（`project-store.js:719-720`、`:755-756`）。超出這個窗之後，復原走「只復原核心」的退路，而這條退路會保留現有附件（`:862-887`）。**前端歷史窗外的核心復原，不解除孤兒狀態**，也不解除來源引用的 `lost` 旗標。只有仍在這個窗內、能整筆恢復附件的那一次復原，才回到原狀。
5. **過期可明選重新取得基底，但不得靜默覆蓋。** 過期＝基底仍是同一物件（未曾缺失）但內容已被別人改過；過期只看基底與尚未 `lost` 的來源引用的指紋，`lost` 不是過期的一種。重新取得基底的預覽**只能做兩方比對**：草稿該欄的原始字串，對現況定義的正規化值。沒有建立當時的舊欄位可做第三方。
   兩方是否相同，沿該欄既有的確認提交解析，不另寫一套。整數毫米走 `int`（`grid-system-workspace.js:115-120`）：先去掉前後空白，再以 `/^-?\d+$/` 與 `Number` 判讀。例：原始字串 `"1830 "` 解析為 `1830`；現況也是 `1830` 則此欄不列入覆蓋；現況不同才列入，並列出現況值與草稿原文 `"1830 "`。解析失敗（如 `"1e"`）一律列入。有號索引走 `signed`（`:122-127`）：`" 001 "` 經 BigInt 成 `"1"`，與現況整數值相同則不列入。
   使用者確認後才把基底指紋更新為現況；之後仍須照常預覽、確認才改 World。曾缺失（`lost`）的來源引用不走重新取得，只能改指向另一個物件（第 4 點）；替換後新引用不帶 `lost`，旗標隨舊引用離開。
6. **D⟨K2a-1⟩ 涵蓋所有未提交編輯資料**：D26–D28 工程與套用草稿、D32–D34 組構規則／配置／實例草稿、網格草稿。數量、唯一性、過期處理由各自契約決定。審查已查證「草稿不阻擋 World 修改」對現有各種草稿成立（原生不知道草稿存在）。
7. **確認一份不動其他草稿**；其他草稿在下次預覽時依 pin 判過期或孤兒，不自動 rebase。

## A3. 首版範圍（一句）

網格來源（D29，含附帶 D19a 規則草稿）與網格配置（D30）的原始草稿可多份並存、各自保存重開與確認；每個已提交目標至多一份非孤兒編輯草稿（開啟即續開）、新建可多份；基底一旦被刪即永久孤兒；來源引用一旦缺失即永久（逐引用旗標 `lost`，隨集合格式保存；任一引用 `lost` 的草稿不得預覽或提交，不論其狀態），只能明選另一個物件替換；過期草稿可經「兩方覆蓋預覽」後重新取得基底；同時只在既有單一工作區開啟一份。

## A4. 資料模型

沿用 `featureAttachments` 信封與 `grid-draft` kind（每 kind 一筆 record，集合在 value 內，沿 #77 `source-rooms` 先例）。

**恰一份、非孤兒、且無任何 `lost` 引用**：沿用現行 `grid-editor-draft/1` 或 `/2` record 與能力，位元組不變，舊 reader 可開。
**其他情形（≥2 份，或含孤兒，或含任一 `lost` 引用）**：
```json
{
  "kind": "grid-draft",
  "schema": "grid-editor-drafts/1",
  "value": {
    "schema": "grid-editor-drafts/1",
    "drafts": [
      { "schema": "grid-editor-draft/1", "draftId": "d-7f3a", "kind": "source", "intent": "create",
        "baseRef": null, "inputRefs": [], "rawForm": { "igName": "客廳", "igUStep": "1e", "...": "..." } },
      { "schema": "grid-editor-draft/1", "draftId": "d-b2e4", "kind": "binding", "intent": "edit",
        "baseRef": { "kind": "grid-binding", "id": 3, "fingerprint": "<64 hex>" },
        "inputRefs": [ { "kind": "grid-system", "id": 2, "fingerprint": "<64 hex>" } ],
        "rawForm": { "igSystem": "2", "igCellJ": " 001 ", "...": "..." } },
      { "schema": "grid-editor-draft/1", "draftId": "d-c9d1", "kind": "binding", "intent": "edit",
        "baseRef": { "kind": "grid-binding", "id": 4, "fingerprint": "<64 hex>" },
        "inputRefs": [ { "kind": "grid-system", "id": 6, "fingerprint": "<64 hex>", "lost": true } ],
        "rawForm": { "igSystem": "6", "...": "..." } }
    ],
    "orphans": [ "d-b2e4" ]
  }
}
```
- 範例中 `d-b2e4` 是孤兒（配置 3 已被刪）；`d-c9d1` 是非孤兒（有效）草稿，但它的來源引用系統 6 曾缺失（`lost:true`），所以不得預覽。
- 元素就是現行單份 value（`/1` 或 `/2`），現有 validator 重用，只有一處差異：`inputRefs` 項目可多帶一個 `lost:true`（只准 `true`，缺省＝未曾缺失；`baseRef` 不帶，基底缺失用 `orphans`），且**只在集合格式內放行**。單份格式的 validator 仍是嚴格鍵檢查（`feature-attachments.js:158、162` 的 `validateReference`），仍拒絕 `lost`，所以恰一份、非孤兒、無 `lost` 時寫的 `/1`、`/2` 位元組不變。`orphans` 列出被標孤兒的 draftId（只能指向本集合中的編輯草稿）。
- **`lost` 旗標**（r3 S1；草稿狀態仍只有有效／過期／孤兒三態，`lost` 與狀態並行）：
  - 設定：來源引用的對象一旦在提交紀錄中被觀察到缺失（任何操作使它不存在，或結果中它不存在），該引用的 `lost` 設為 `true`，永久。保存時隨該引用寫入集合格式；含任一 `lost` 引用的草稿因此不能寫回單份格式——單份格式沒有欄位，寫回會讓旗標遺失，之後同 id 同內容的新物件又會對上 pin。
  - 效果：任一引用 `lost` 的草稿不得預覽或提交，不論其狀態是有效或過期；仍可保存、重開、捨棄、把該引用改指向另一個物件。`lost` 引用保留最後記錄的 `fingerprint`，不參與過期比較。目標唯一性只看是否孤兒，與 `lost` 無關。
  - 不可清除（依 D57／I68／R54）：同一 `draftId` 的 `setGridDraft` 新值中，既有 `lost` 引用必須原樣保留，或明選另一物件並確認替換；純移除引用、清空 `inputRefs`、保留同 `(kind,id)` 卻去掉旗標均拒絕，參數來源亦核 `(parameterId,fieldId)` 與對應 raw 欄位，不准只保留另一個既有引用來掩蓋純移除。`repinGridDraft` 只更新尚未 `lost` 的引用。只有改指另一物件時旗標隨舊引用離開（M14b）；整份草稿的明示捨棄另依 R54，不是同一草稿純刪引用。
  - 對象不存在而未帶旗標（舊版客戶端存檔、手改檔案）：validator 不因此拒絕專案，匯入後首次載入的掃描補標（見下「孤兒與 `lost` 掃描」）。
- 依 `draftId` 字典序正規化保存；陣列位置與顯示順序不是身分。
- 約束：`draftId` 唯一；同一 `(baseRef.kind, baseRef.id)` 的**非孤兒**編輯草稿至多一份（不論其引用是否 `lost`）；`lost` 只能是 `true` 且只出現在 `inputRefs` 項目；≤16 份；每份 ≤128 KiB；本 record ≤1 MiB；信封仍 ≤8 MiB（份數／位元組為工程暫定值）。
- 新增或內容變更的接納，須先計算最壞自動補標後的 UTF-8 JSON bytes：每個 `inputRefs` 全部補 `lost:true`、每個有編輯基底的 draftId 全列入 `orphans`，包含單份→集合的 record／外殼、實際格式／能力與完整 manifest；逐層核每份 128 KiB、record 1 MiB、信封 8 MiB，計入 draftId 的實際編碼與跳脫，不只算 raw 或固定常數。超出在接納前原子拒絕，不等 World 刪除／保存時才失敗。
- 已保存合法內容沿 P-059 只放行自動 lost／orphan／必要集合升版的精確增量；扣除後仍須符原適用上限，raw／ruleDraft／身分逐字保留，不授予一般 payload 信用或新增可信歷史旗標。重存同內容保留例外，新增真實內容回新接納預留；既有集合不可強折成配額較小的單份。讀取補標、World 刪除、保存與冷重開均不能因此阻擋或丟資料（M17／M18）；#201 的已裁決實作須隨交付核收，不稱本 head 已有 runtime。
- `requiredCapabilities`：`grid-editor-drafts/1`＋各元素實際用到的 `grid-editor-draft/1`／`/2`。現行 `:283-284` 拒絕同時宣告 `/1` 與 `/2`，本 PR 須放行（見 A7）。
- **專案格式號**：`geometry-canvas/1`–`/16` 已全數占用（`project-store.js:8-19`：/13 GRID_RULE、/14 SCENARIO、/15 CASE、/16 SECTION 等）。本提案用佔位 `geometry-canvas/⟨K2a-F1⟩`，寫入時由共用格式 owner 配號，並加入 `project-store.js` 各格式允許清單（約 `:310-337`）。
- **格式號逐版向上相容**（A、B 共用）：較新的讀取端必須接受較舊格式號裡已經合法的內容。A、B 分兩個 PR，誰先合併未定。後合併的一份必須接受先合併那一份的新內容（新格式號、新能力、新附件形狀），不得只認自己這次加的格式。兩邊平行開發時若都想佔下一個號，後合併者要在自己的格式上讀得開先合併者已經寫入的內容。

- 只替換／捨棄指定 `draftId` 那份；新值 `draftId` 須等於參數；若為編輯草稿且已有另一份**非孤兒**草稿指向同目標 → 拒；新值若抹去旗標或純移除既有 `lost` 引用 → 拒（見上「`lost` 旗標」）。`repinGridDraft` 只更新基底與尚未 `lost` 的來源引用的指紋，絕不清除 `lost`。

# B 部：#25 重複開間生成（含主格線定位）

## B1. 問題

D34/I42/R35 只生成兩支 primary＋一支 secondary。關鍵在**主支不能共用**：每個實例自己擁有兩支主支，兩個實例不能共用中間那支（會在同一條線上各生成一支 → I11 碰撞）。
所以生成器最多只做得出**一個開間、一支副支**。定位又只收 D6 參考線，而 `WORLD_MAX_GUIDES = 16`（`current_geometry.c:3612`），一間房的骨架線就不夠用。

## B2. 物理模型（先模擬，再剪枝）

平釘天花骨架（`flat-nailed-ceiling` §4、§④、⑤②）：主支整支通長、兩端坐在邊界材上；貼著與主支平行的牆那支也是主支（I21 邊界主支）。副支段化，塞在相鄰兩支主支之間，各開間的副支在同一組線上（366 記號打在邊界材上）。
一條副支線橫越房間，被內部主支切成段，**每段兩端就是它所在位置左右最近、實際存在的主支**。推得出：
1. 骨架＝規則局部接合在每一對相鄰主支上重複；不需新接合種類，不放寬 D15/I19（boundary 1 < primary 2 < secondary 3 處處成立）。
2. 相鄰要逐條副支線判定（只算完整涵蓋副支寬度帶的主支）。
3. 內部主支同時是左開間的右主支、右開間的左主支 → 規則的兩個 primary member 必須同槽位（一支料一個截面）。
4. 副支段存在的理由是「這兩支支撐之間的一格」；格子改變時舊段不是新段的延續 → 刪舊建新。
5. 自我反駁：反組法違反主骨通長；ortho-split 在內部主支處的幾何已被本模式涵蓋；格線錯縫描述板縫，不是骨架線。三者都不是首版必要。

## B3. 首版範圍（一句）與選項理由

**首版：同一單一開間規則可在一個實例內重複套用於有限多支主支（2–12）與多條副支線（1–24），開間逐線推導；定位可用 D6 參考線、承載面主格格線（有限索引或配置主格的 signed k），主支另可貼外輪廓邊；主支支撐與定位不得依賴本實例的料。**

- **重複展開**是唯一能讓生成器做出真實天花骨架的項目。4000(橫越主支)×3000(沿主支) 的房間要 6 支主支（含 2 支貼牆）、8 條副支線、5 個開間共 **40 支副支**，合計 46 支 owned（R8 更正）。
- **主格線定位**是必要配套（參考線上限 16 條）；at-line 主格線引用（I13）原生已支援。
- 一個 PR 的量：原生在既有三件求值外加迴圈、身分表與差異；不新增接合語意，不放寬公理底線。

未支援清單逐項處置（不排程，每項寫明阻擋點）：

| 項目 | 首版 | 阻擋點／何時再做 |
|---|---|---|

| ortho-split 規則 | UNSUPPORTED | 幾何已由本模式涵蓋；要接受此寫法須先定「遠端未指定的副支端」支撐契約 |

## B4. 資料模型

`assembly-generation-transaction/1` 的 `create-instance`／`edit-instance` value 加 `layout:"bay-repeat"`；沒有 `layout` 的舊形狀＝D34 單一開間，不變。

```json
{
  "id": 2, "name": "主臥天花", "bindingId": 1,
  "rule": { "id": 1, "version": 1, "fingerprint": "<64 hex>" },
  "surfaceId": 1,
  "layout": "bay-repeat",
  "primaries": [
    { "key": 1, "at": { "kind": "outline-edge", "edge": 3 },
      "ends": { "start": { "kind": "timber", "id": 90 }, "finish": { "kind": "timber", "id": 92 } } },

```
- `key`：實例內唯一正 uint32（主支、副支線各一命名空間），編輯器從 1 起取最小未用者；位置改了 key 不變＝同一支料。
- `at`：主支 ∈ {`guide`, `grid-line` axis=u, `outline-edge`}；副支線 ∈ {`guide`, `grid-line` axis=v}。`gridId` 須是該承載面主格；`index` 以十進位字串精確保存。帶相位差的格線、子格線、規則線、孔邊、角材側面 → UNSUPPORTED。
- `ends`：沿 R21 無序 between，只收非本實例的已放角材。SELF_SUPPORT 的依賴閉包只算兩種：明示的引用，以及實際被選為端面的擋面；此閉包不得含本實例 owned 角材。
- 主支 +v、副支 +u、深度 +n；binding 須 contactFace=A、orientation=A；規則須為單一開間拓撲且兩個 primary member 同槽位。

- 所有權對應（`assembly-read` 回傳）：`{"primary":k,"timberId":t}`、`{"secondary":{"line":l,"left":a,"right":b},"timberId":t}`。
- 場景行（候選，原生 owner 定稿）：`owned <instance> bay-primary <key> …`、`owned <instance> bay-secondary <line> <left> <right> …`；`requires assembly-bay-repeat/1`。

- 格式號：佔位 `geometry-canvas/⟨K2a-F2⟩`（/1–/16 已占用）。逐版向上相容與合併順序的要求同 A4：後合併的一份必須接受先合併那一份的新內容。

## B5. 求值、身分與更新

求值（R⟨K2a-2⟩）：
1. 驗能力、規則拓撲、primary 同槽位、binding 完整、容量。
2. 驗依賴：SELF_SUPPORT 的依賴閉包只算兩種——明示的引用，以及實際被選為端面的擋面。此閉包不得含本實例 owned 角材；違反回 `UNSUPPORTED`，診斷碼 `SELF_SUPPORT`（指名支撐或引用、依賴路徑、被依賴的 owned 角材）。
3. 每支主支依 `at`＋`ends` 走既有 place／R6／R21／I19，求 footprint 與長度。求值沿 I9／R6，同一承載面上 World 順序較早的料先求值；**求值對象是「已扣除本候選將刪除的 owned 角材之後的候選 World」**。否則「順序較早的料」字面上會含本候選將刪的舊副支（BR04 在 u=1000 插主支時，World 順序較早的舊 (k500,k1500) 副支會撞上新主支）。
   - **將刪集合怎麼得到**（自行補充）：將刪集合＝步驟 4 推出的格子集合與舊 mapping 的身分鍵差異（步驟 6）。這個差異只需要各主支沿 v 的範圍與 `omit`。**身分差異與將刪集合所用的主支範圍 = R21 `between` 兩個被點名擋面的 fixed 座標，直接取座標、不經 R6 碰撞求值（`current_geometry.c:8078–8080`）；之後正式求值若得出不同範圍或失敗，整筆拒絕。**範圍因此不看 World 內有沒有 owned 角材，所以先算出主支範圍與身分差異，再在扣掉將刪者的候選 World 上依序求值，不會循環（見自檢 10）。不用「主支的 `at`／`ends` 依步驟 2 不依本實例 owned」當理由：那只保證依賴不含 owned，而 R6 的區間檢查會看 World 內所有已放角材、含 owned（`current_geometry.c:7853–7917`），含 owned 與扣除將刪者之後的 World 對同一組 between 可以得出不同區間。
   - **World 放置順序**（`++next_order`，現行 `assembly_generation.inc:115`；保留者沿用原順序，見 `:85`）：新建的 owned 角材接在 World 末端。同一候選內，主支依其 key 升序依次取得順序，副支依副支線 key 升序接在全部主支之後；同一線內依左 key、再右 key 升序（同線 tie-break 為自行補充，讓順序確定，見自檢 9）。
   - **id** 不是順序，由步驟 6 另行規定。
4. 每條副支線 y：取沿 v 範圍完整涵蓋副支寬度帶的主支；有主支只部分覆蓋該寬度帶 → 拒絕並指名（【選擇】，代價見 B-5）。涵蓋者依中線 u 排序，相鄰兩支＝開間。沒有開間或格子全被略過時，該線生成零支（合法，R2）。
5. 扣除 `omit`；其餘每格以 `between t<左> t<右>` 唯一解出跨距並過 I5/I11/I19/R6。任一格失敗整筆拒絕，列出全部失敗格與條號；不自動略過。
6. 依身分鍵比對新舊；**外部引用檢查以格子身分鍵在配發新 id 之前判定**；**本候選刪除的 timber id 不得配發給本候選新建者**（F7，現行 `assembly_generation.inc:115` 由 1 找最小空號，須排除）。這裡配發的是 id，與步驟 3 的 World 放置順序是兩件事。
7. 全量驗證 → 預覽 → 確認同一候選 → 保存。

身分：主支（實例、主支 key）；副支（實例、副支線 key、左 key、右 key）。
- 主支改位置、截面、網格間距 → 同 key 保留 timberId，重算（I8a 預覽）。

## 仍推不出唯一行為、或我最不確定之處

1. **孤兒判定的盲區**：依據是「本專案提交紀錄觀察到的基底缺失」，來源引用的曾缺失同樣只看這份紀錄。若刪除與同 id 重建發生在本專案看不到的地方（舊版客戶端編輯後存檔、或外部改 scene 再匯入），重開時對象存在且內容相同，就無法分辨。要完全封死需核心為這些物件加「建立序號」之類的身分（動 D29/D30 定義），本版不做，列為殘餘風險。
2. **核心回執是否列出本交易刪除的物件**：孤兒掃描與來源引用的曾缺失都要靠它判「同一交易內先刪後建同 id」。我沒讀到現行回執格式，若沒有，A 部 PR 須在原生補上。
3. **SELF_SUPPORT 的依賴閉包**（r2 已寫死）：只計明示的引用，以及實際被選為端面的擋面。不再用「線、邊、擋面、角材之遞移閉包」，也不寫整塊求值。新建 owned 的 World 放置順序接在 World 末端，主支在前、副支在後（組內次序見 B5 步驟 3）。材料綁定上的截面來源若指向本實例 owned，這句沒有寫進閉包。
4. **R6(e)／BR03 的 B2**：手放 B2 的延伸段停在實例 L 的 owned 主支上，屬外部引用，會阻止刪除實例 L 或改動那支主支使 B2 失效；這是預期行為，但會讓「編輯實例 L」常被 B2 擋下，使用體驗待實測。
