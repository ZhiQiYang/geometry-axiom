## 一、現況與依賴順序

此 main 已有 PF-2，不是只有 PF-1；但已有「試排」不代表已有「試排的原生衍生宿主」，也不代表已有有效板縫、承接比對或 R45 建議角材。PF-2 明確保留 partial native capability，沒有宣告完整 panel-fill/1 實作完成。現有定義與輸出界線見 [geometry-core/panel-fill/PF2-NATIVE.md:1–95](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/panel-fill/PF2-NATIVE.md#L1-L95)。

採用目前可核對的切片順序：**PF-2 → PF-H 原生衍生宿主 → PF-3 承接比對 → PF-6 建議角材 → PF-4 網格對齊 → PF-5 空間完成面 → 模板實作前的真宿主見證 → 模板。**

這裡有兩個容易混淆的地方：

- GEO-255 原切片與模板提案較早把衍生承載面放在 PF-2 描述；後來 P-098 把宿主抽成 PF-H，且要求「真宿主足跡、移除接入負控制、#221 原生宿主見證」。不能因此再等到 PF-5 才做宿主。來源：[BACKLOG.md:173–180](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/BACKLOG.md#L173-L180)、[#227 的 P-098 交付範圍紀錄](https://github.com/ZhiQiYang/geometry-axiom/pull/227#issuecomment-6149335672)。BACKLOG 仍寫等待 PF-0 是舊進度文字，不能取代此 SHA 已存在的 SSOT／PF-2 程式。
- [P-094](https://github.com/ZhiQiYang/geometry-axiom/pull/221#issuecomment-6146155291)要求 PF 各片落地後才開始模板；一般 placement 上的 D7 對照不是模板所需的衍生宿主見證。模板五步、逐跨副支都要在同一候選 World 求值、一次提交。[geometry-core/framing-template/PROPOSAL.md:124–140](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/framing-template/PROPOSAL.md#L124-L140)。

**目前阻塞**：P-103 已把原 E1 限定為純演算法 oracle，另要求 E1-legal；但其 E1-legal 指定的 V 向 secondary 又與兩端 boundary 推導出的主支軸發生 I21 衝突。#227 正文已回報這一點，不能把 PF-H 當成已完成。此處只回報裁決文字與 SSOT 的衝突，不更改角色裁決或條文。來源：[P-103](https://github.com/ZhiQiYang/geometry-axiom/pull/227#issuecomment-6152304537)、[PR #227](https://github.com/ZhiQiYang/geometry-axiom/pull/227)。

## 二、三片共同接在什麼資料上

**已存在的原生定義**：`FinishSurface` 保存 D3 邊界、D2 框架、s、具型別柱樑引用；`PanelFill` 保存完成面 id、固定材料版本、length 軸、起點、縫寬／相位差來源、D44 ParameterRef。不是把畫面或裁切多邊形保存成第二份真相。[geometry-core/finish_surface_types.h:1–37](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/finish_surface_types.h#L1-L37)。

**已存在的推導工作區**：`PfLayout`／`PfTile`／`PfFragment`／`PfLoop`／`PfSeamLine`；其中 seam line 不等於「兩側確實有板的有效縫段」，也不等於衍生承載面上的可見主格線。PF-2 `pf_values()` 已解析 t、來源與面材層裁切，不能再在 JavaScript 複製另一套幾何計算。[geometry-core/panel_fill_layout.inc:1–74](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/panel_fill_layout.inc#L1-L74)。

**PF-H 必须供給後續的能力**：R41 真正的來源試排衍生宿主，含 h 來源、板背框架、角材層有效區域的各分量、穩定衍生邊鍵及既有 D7 求值接入。不能只畫一張相同位置的一般面。R43 只納入「宿主 id 就是該試排衍生宿主」的角材；共面但屬於別的宿主也不能冒充。來源：[公理層.md:1682–1722](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1682-L1722)。

後續需要的內部資料結構名稱尚屬實作設計，不是新增公理；可以保存候選描述／查詢結果，但正式 World 仍只保存 D41／D42、D4 衍生宿主保存欄位、來源主格及已確認 D7 定義。

## 三、PF-6：建議角材，R45

### 原生能力與接點

1. **輸入與候選描述**：一份試排、全批共用的 A／B 明確來源、兩軸角色、使用者明選的候選集合。每個候選至少能追溯至衍生邊鍵或縫線完整身分、角色、方向、through、R6 結果及逐項診斷；未確認不能消耗正式 id、寫 World 或 history。交丁被錯開軸本版限定 secondary，不能替使用者交換角色。D44 的 X 是承接門檻，不是角材生成尺寸。[公理層.md:601–650](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L601-L650)。
2. **宿主／主格**：呼叫 PF-H 的宿主能力；不存在時以選定 B 來源建立 h，已存在則 B 有效值必須等於 h。R45 本身要求尚無主格時建立 from-fill 主格，因此 PF-6 已需要最小原生 from-fill 能力，不能因「PF-4 排在後面」而用普通網格替代。PF-4 承接完整對齊、值快照與互動，不是推遲 PF-6 的必要前置。已存在主格卻不是本試排 from-fill 時整批拒絕。
3. **候選生成與順序**：各分量 FIXED 外環垂直主支軸的邊產生 boundary，平行者產生邊界 primary；跳過已覆蓋的對應邊，FREE 說明不產生，孔環不產生。再將「有效板縫段」與角材層各分量相交，每個正長度極大區間取映射後中點，依 R6 求跨距；同線／band／跨距才去重。固定順序為 boundary → 邊界 primary → 板縫 primary → 板縫 secondary，後者看得到前者。注意「u 縫」是 u 恆定、沿 v 走，不得把縫線軸標籤直接當主支走向。[公理層.md:1731–1746](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1731-L1746)。
4. **預覽／正式建立分離**：預覽列所有候選與各條不成立的原因；使用者選完後，以 fresh 候選重新依同順序全量驗證。任何一項違規，全批不提交；不是默默刪掉紅候選，只交綠的。沿用 R6、I5／I6／I11／I19／I20／I21／I22，不另造一套比較寬鬆的放置器。PF18 的角柱／凹口案例本來就可能全選被拒，不能把「有建議」寫成「保證全部可建」。
5. **與模板的界線**：R45 不補板中間支撐、吊筋或樓板連接。模板柱邊料是一般 D7 宣告；模板板端縫副支必須逐跨生成，不能用 R45 一個中點只挑到一跨。F5 的六跨已列在 [geometry-core/framing-template/PROPOSAL.md:126–140](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/framing-template/PROPOSAL.md#L126-L140)。

### 特別結論：R45 能否放進外層交易？

**現在的答案是：有共用候選交易基礎，但沒有已實作的可組合 R45 能力，不能直接使用現有 confirm 來冒充。**

- 已有 `batch_preview()` 複製一份候選 World，依序執行 operation callback，再全量重驗；這是可沿用的原子交易基礎，不需要另造第二套 history。[geometry-web/engineering_bridge.inc:86–116](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-web/engineering_bridge.inc#L86-L116)。
- 但 `batch_confirm()` 會直接 `history_record`、把 after 還原到正式 `g_world` 並增加 revision；它不是「只把結果加進呼叫者候選」的函式。同時 active history group 會被拒絕，不能用 history 分組替代真正的一次提交。[geometry-web/engineering_bridge.inc:122–135](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-web/engineering_bridge.inc#L122-L135)。
- 現行 `fs_operation()` 只處理完成面／試排 put、delete，沒有 R45、衍生宿主、一般 D7 外層組合操作；它刻意拒絕預覽未揭露的其他定義變更。[geometry-core/finish_surfaces.inc:234–251](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/finish_surfaces.inc#L234-L251)。

**實作方向（工程建議，不是新增條文）**：把「在呼叫者持有的 candidate World 上生成／驗證／加入選定 R45 操作」做成不提交的原生能力；外層統一處理 fresh 檢查、完整預覽、正式 id 與最後唯一一次提交。不得在 R45 內呼叫另一輪會從 `g_world` 起算、覆寫全域 preview 的 `batch_preview()`，更不得內呼叫 `batch_confirm()`。

需要改動的邊界是：PF-H 宿主 candidate 操作、PF-6 候選生成與選取操作、PF 交易 dispatcher／完整預覽，以及依賴重驗的接線；**不是刪除既有變更守門**。如果外層一併建立參數、一般 D7 或模板逐跨料，這些也必須逐項揭露，不能只是放寬 `fs_operation()` 白名單而保留舊的不完整預覽。

必要回歸：在同一候選完成「宿主→外環 boundary→柱邊 primary→柱邊 secondary→R45→逐跨副支」後，故意使最後一支違規，正式 World、metadata、dirty、id 高水位與 history 均不變；成功時只新增一個完整復原步驟，Undo／Redo 包含 R45 前後所有操作。再移除原子提交接線，原負例必須轉紅。這是待執行驗收設計，不是已完成測試。

### PF-6 驗收對應

主責 PF10、PF14、PF15、PF18、PF20、PF21；共同承擔 PF07／PF11／PF13／PF19，以及 PF08／PF09 的角材端點實體結果。PF05／PF06／PF23／PF24 的承接算法歸 PF-3，但 PF-6 新建角材後必須接回其結果，不能另算或省略。PF14 的 h／B 同交易修改尤其能驗出是否錯做成多次提交。

## 四、PF-4：網格對齊鋪排

### 原生能力與資料

**live from-fill 主格**與**普通 D29 值快照**是兩種不同承諾，不能共用同一份含糊的「網格資料」。

live 主格要引用試排與正確衍生宿主；保存正式來源與線身分，不保存畫面裁切段序號。使用 PF-2 共用精確公式，在完成面座標求 c／band，再按 R41 映射到板背框架。s=−1 時 v 座標可能隨 k 遞減，但 signed k 身分不能重排；band 是板列 p，不是 D29 cell 索引。修改上游後，完整重算 guide、角材與承接，失去唯一引用則拒絕，不找最近線重綁。來源閉包與 I8a 預覽都要包含新型別。[公理層.md:620–630](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L620-L630)、[公理層.md:1216–1235](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1216-L1235)。

明確導出的 D29 快照則把當下 P、g、a 存成普通整數值，不引用試排／材料／邊界。交丁軸必須轉為 **anchor=a+δ、stagger=−δ**，補償 D43 板列與 D29 cell 的奇偶差；其他軸仍保存當下值。試排後續變更不能帶動快照；之後 D30 明選錨點平移照舊。[公理層.md:1723–1730](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1723-L1730)。

**接點**：PF-2 `PfSeamLine`／共用 lattice 數學 → PF-H 板背框架与有效域／邊鍵 → PF-6 已需具備的最小 from-fill 原生能力 → 完整 reference／查詢／預覽／保存。衍生面頂點引用依 R41 不支援，需用合法衍生邊鍵座標；不是在 UI 另外創造頂點 id。

### PF-4 驗收對應

主責 PF02、PF03 的跨表示精確對照，PF07、PF17、PF19、PF21、PF22 的引用／band／鏡像；共同 PF11、PF12、PF13。尤其要做：負 k、負奇數 band、s=−1、奇數縫寬、快照建立時逐線相等／建立後互不連動，以及障礙把引用邊拆段後整笔拒絕。

## 五、PF-5：空間完成面，高度、方向、樑

### 原生能力與資料

這一片是把完整空間流程接到已有 D41 和 PF-H，**不是首次發明高度或衍生宿主**。完成面框架／s／typed 障礙引用現已存在；PF-2 提供材料 t 及面材層結果；PF-H 必須提供 h、角材層、原生宿主與邊鍵。介面只明選資料、顯示原生結果，不能從畫布位置猜實際高度，也不能按附近位置自動納入柱樑。[公理層.md:601–608](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L601-L608)。

核心結果至少須分清：每件障礙的 R_k／沿 n 的 q、與 F 的平面關係、面材層是否遇障礙、角材層是否遇障礙、各層裁切結果、板背框架与缺失的 t／h。D41 在還沒有 t／h 時允許明示缺項，不得報成已通過兩層。

R41 的板背框架是 **(O+t·n, U, s·V, n)**，n=s·N；兩層分別是 q∈[0,t] 與 q∈[t,t+h]，以正體積交集裁切。板背或角材頂恰貼樑底時只是接觸，不得補 epsilon 變成相交。垂直完成面沿自己的 n 判斷，不是所有案例只比世界 z。[公理層.md:1206–1212](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1206-L1212)、[公理層.md:1682–1700](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/公理層.md#L1682-L1700)。

需要接入的更新操作是完成面 O／U／V／N／s、明選障礙集合、柱樑定義、材料版本以及 h 来源；一次重算完整下游。樑把 G 分裂時保留各分量；空 G 合法但不能放材；退化環不能用 bbox 補洞。包樑側面與底面各建另一完成面，不能自動擴張成整個包樑功能。先前 apply-proj 已切掉的 F 不會因完成面降低就自動還原。

### PF-5 驗收對應

主責 PF01、PF04、PF08、PF09、PF14、PF16、PF18、PF20、PF22 的空間及雙層整合，共同 PF07／PF11／PF12／PF13／PF19。關鍵固定數字：樑 z=[2500,2800]、t=9、h=30；完成面 2600 兩層遇樑、2400 兩層通過、2480 只角材層遇樑；2491 板背貼樑底、2461 角材頂貼樑底，要保留開區間政策。這些是待驗 oracle，不是本次實跑。

## 六、PF01～PF24 的來源與驗收邊界

上述片別分工是依切片目標整理的**實作責任建議**，不是改寫驗收表。PF01–PF22 原表：[geometry-core/panel-fill/AXIOM-DIFF-r2.md:490–516](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/panel-fill/AXIOM-DIFF-r2.md#L490-L516)。PF23／PF24 另在 [geometry-core/panel-fill/amendment-r2.1-R43.md:57–85](https://github.com/ZhiQiYang/geometry-axiom/blob/0eb447e00605f6df117711b03e6c98ccabbcd026/geometry-core/panel-fill/amendment-r2.1-R43.md#L57-L85)，不是可以在 r2 表中找到的兩列。

PF05／PF06／PF23／PF24 主要驗 PF-3 承接；PF23／24 原數字只能作純算法輸入。真宿主整合另用 P-103 的 E1-legal 分工，且角色衝突須先釐清。原生 dump/replay 綠不等於 PF11 全新瀏覽器 profile 正式專案重開已過；各片新增的能力、來源閉包與確認角材都須真正保存重開。沒有新 UI 的切片也不能因此宣告後面的 UI 已驗收。

## 七、條文未定／契約未定／不能自行決定的部分

**條文未定**：GEO-255 提及的「窄條」沒有在本次 D41–D45／I52–I57／R41–R46 定出獨立數值門檻；不能拿 D44 的 8 mm 承接門檻當窄板寬度，也不能新增阻擋紅試排保存的條件。需另確認規範來源與是否只作提醒。

- 反例：`"9." + "0"×62`，64 bytes，也精確為 9 mm。

材料發布使用 `thickness[128]`，第二個字串符合其正十進位語法且可完整保存，沒有超出該材料讀取緩衝區；canonical JSON 也不會替字串刪掉尾端零。PF-2 的 `pf_values` 卻再以 `thickness[64]` 讀同一份已發布材料。`eng_json_string` 遇 `strlen >= capacity` 直接回 false，接著 PF-2 統一回 `I52: ... positive integer mm ... no rounding`；`fs_error` 將分類设為 INVALID，預覽因此報 `PANEL_FILL_INVALID`。

## 二、可能的風險

### P1｜面積精確整數與 JavaScript 解碼精度沒有接合

[geometry-web/panel_layout_bridge.inc:7–9](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/panel_layout_bridge.inc#L7-L9) 用十進位 JSON number 輸出 `area`；原生面積累加在 [geometry-core/panel_fill_layout.inc:92–98](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-core/panel_fill_layout.inc#L92-L98)。一般前端解碼是 [geometry-web/app.js:648–670](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/app.js#L648-L670) 的 `r.json()`。

幾何候選：F=[0,99999999]²，同樣尺寸的一片板，t=1、gap=0、起點 0、無障礙，全部座標與單邊尺寸都在 D1；只需一片，不以「板片很多」排除此例。精確面積為 `9999999800000001` mm²，仍可放入 int64。自製 Node 見證實際得到：

```js
const exact = 99999999n * 99999999n;
const value = JSON.parse('{"area":' + exact + '}').area;
String(exact);          // "9999999800000001"
String(BigInt(value));  // "9999999800000000"
```

**已確認的是這種 wire 格式經普通 JavaScript JSON 解碼損失 1 mm²；尚未確認正式 PF UI 的影響。** 上面 wire 是依原 serializer 格式構造，不是本輪 C bridge 抓包；目前 PF-2 明示沒有正式顯示／完整專案 UI。本項因此列為接入風險，不宣稱 C 面積算法算錯。T2 應在真正 C→HTTP→JS 路徑核對精確值，再決定無損整數欄位／解碼契約；不能只驗 `Number.isInteger`，因為失真的結果仍是整數。

### P2｜零板片時，外層列舉工作未被 1024 個本體候選上限限制

[geometry-core/panel_fill_layout.inc:129–163](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-core/panel_fill_layout.inc#L129-L163)：`enumerated` 只在內層真的列出板本體時增加。這是公開的本體候選上限，不是外層 row 的工作上限。

反例取 Pu=Pv=1、g=1、a=(0,0)、直排、F=[0,100000000]×[1,2]，無障礙。整個 F 的 v 範圍恰在板縫內，沒有正面積板本體。代入現行公式：

- row=u：first=0、last=49,999,999，共 **50,000,000** 輪。
- 每輪 along=v：a=1、z=0，內層不執行，`enumerated` 一直為 0。
- 後面的 seamLines 才會遇到 4096 上限並回 CAPACITY；前面的空迴圈已發生。

這是可直接重算的工作量反例，不是已量到五千萬次迴圈耗時，也不能據此宣稱已找出 #209 的 15 秒根因。T3 先量 row 次數、候選數、CPU／wall time；可研究提早判定空軸及 seam 容量，但不得刪掉合法的零片定義或把 raw seamLines 與有效板縫混為一談。

### P3｜原生確認不能直接套上現有一般前端 API 流程就算完整接入

[geometry-web/app.js:615–703](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/app.js#L615-L703) 的變更守門、requestId 配發、definition-changed 通知名單有 engineering／assembly／section-profile-confirm，沒有 panel-fill-confirm。另一方面 [geometry-web/serve.py:167–203](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/serve.py#L167-L203) 在沒有 requestId 時直接送 bridge，不建立這次操作的結果回執。

**推測／條件式風險：**未來 PF UI 若直接用目前 `apiRequest('panel-fill-confirm ...')`，可能在結果遺失時沒有相同的回執恢復路徑，也缺乏對其他工作區的變更通知。原生 token、revision 與全量重驗仍有保護；本項不等於 native 可以任意重複提交。現在沒有正式 PF UI，因此不把它升格為已發生的畫面事故，也不要求本片提前做 UI。T7 在正式接入時驗收到、遺失、延遲、跨專案與重送拒絕。

### P4｜派生序列化再次求值失敗時，外層成功旗標與內層 error 的契約需補強

[geometry-web/panel_layout_bridge.inc:4–6](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/panel_layout_bridge.inc#L4-L6) 在 `pf_build` 失敗時只輸出 `derived:{error:...}`；[geometry-web/panel_fill_bridge.inc:70–99](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/geometry-web/panel_fill_bridge.inc#L70-L99) 的 read 外層仍是 ok:true，preview.valid 也來自先前的候選驗證。

**推測：**先前重驗成功、之後序列化重算才發生 malloc/realloc 失敗時，使用者可能拿到 valid:true 卻沒有完整 after 幾何的預覽。這裡保留 inner error，因此不是「完全隱藏錯誤」；尚未讀到完整接收端如何處理這種回覆，也沒有注入 allocator 失敗。T8 用精確一次性注入確認：不能把不完整預覽當成完整候選展示並直接確認；不得用舊 cache 假裝本次成功。

### P5｜突變工具有「assertion 失敗與測試 error 並存」仍可接受的驗核縫隙

這是對未來證據生成器的風險，不推翻既有原件：[panel-mutants.stdout:1–12](https://github.com/ZhiQiYang/geometry-axiom/blob/79412a858f712981fa0ba15a6b293c3e0bf06f21/tests/evidence/pf2-b1-bands-20261014/panel-mutants.stdout#L1-L12) 十個變異目前全部 errors=0，baseline/restored 各17項通過。另，工具在同一 Python 行程內跑 unittest，`test_exit` 是由 `wasSuccessful()` 換算的結果碼，**不是每個 test 的 OS 子程序退出碼**；compile_exit 才是編譯子程序 returncode。不得把兩種計數混稱。T8 可用合成「指定 failure＋額外 error」驗證工具會拒收，不改歷史收據。

### 5.1 完成面設定

先選此 D3 面下既有完成面或建立完成面；同一 D3 的多份定義均列名稱與可辨識身分。使用者明填完整框架、結構側，從具型別清單明選柱／樑；沒有隱藏高度、方向、結構側或障礙預設。

「填入目前放置框架」須先列 O/U/V/N，說明是本次值輸入，不宣稱日後跟隨原放置。沒有 D4 放置不阻擋合法 D41；仍須有完整明選框架才可提交。

障礙逐件顯示與 F 為內部相交、只接觸或分離，以及各層判定；尚缺 t／h 時顯示缺項，不虛構通過。包樑側面與底面另建完成面，不由本操作自動補齊。

### 5.2 鋪排設定

選固定材料版本，並列 width／length／thickness 的來源與有效值。length 軸、起排點、縫寬來源、直排／交丁、交丁軸與相位來源、門檻 ParameterRef 都可明讀。

切直排明確移除交丁設定，預覽列此差異；材料版本改選不暗升其他試排。缺厚度、9.5／12.5 mm、未知引用、不合法 gap／stagger 由原生拒絕，不自行取整或依名稱猜值。來源選取共用既有 typed source 控制；保留材料版本、parameterId／fieldId 與 length／width 的欄位映射。

### 5.3 預覽與結果

同一次完整預覽顯示來源設定、完整裁切片／孔、整片／裁切片數、有效板縫、承接子段，以及受影響網格、guide 與角材。

板片、有效板縫、衍生宿主可見格線是不同圖層；nonSeams 不塗成承接不足。每段列左右實寬與 X；紅／綠之外有文字與線型。零片可合法，1 mm 裁切片保留真尺寸；不加入未採納的窄條門檻、刪片或拒絕。只改 X 時列出比對變化，不假造幾何移動。

容量不足、部分資料、內層 derived error 或超時均不能顯示上次成功圖冒充本次完整預覽。保留輸入與清楚原因，可重新預覽或取消。

### 5.4 確認、no-op 與歷史

「確認本次變更」只提交剛才同一完整候選。合法而承接不足仍可保存；幾何違規、來源不明或不完整不得確認，指名對象與條號。

沒有實質定義 patch，或正規化後正式定義完全不變，是 no-op：不送提交、不新增 history／revision／dirty。只改來源而有效值相等仍是定義差異，不當 no-op。成功實質變更一次 Undo/Redo 還原本次所有正式定義及依賴。

### 5.5 PF-6 建議角材

在同一結果區的後續動作選「建議角材」，明選 A／B 來源與兩軸角色。候選分別列固定外環邊材、邊界主支、板縫 primary／secondary、FREE 邊及各項失敗原因；暫時鍵不能冒充正式 id。

使用者明選集合後，原生於同一 fresh 候選按 R45 順序重驗。取消一項使另一項失去支撐時整批拒絕，不偷偷加回、不只建成功者。必要宿主、from-fill 主格與角材都列於同一確認，確認前不配正式 id。

嵌入模板時沿模板的外層 owner，PF 子面板不能自提交通用 confirm；單獨 R45 才由 PF 擔任外層 owner。已存在的 assembly／pair／其他成組約束照常參與全量驗證，不能將 owned 成員轉為普通 D7 修補候選。[R45:2410–2425][r45]

### 5.6 PF-4 活引用與值快照

後續動作使用兩個清楚名稱：「建立跟隨試排的網格」、「導出不跟隨的網格快照」。

前者的有效值唯讀，可返回來源試排編輯；後者明告建立獨立普通 D29，後續改試排不跟動。既有不相容主格不暗換。signed k、band、負側映射與交丁快照轉換都取原生結果，不以最近線、顯示序號或相同數值改綁。一般 grid 編輯器只呈現其合法來源模式，不能以手改有效值繞過 from-fill。

### 5.7 PF-5 空間修改

高度、方向、結構側、障礙回同一完成面編輯器。預覽同時展示面材層、角材層、板背框架與既有角材的完整影響。既有 apply-proj 形成的 F 缺口保持，不猜測再補回或二次裁掉。這是既有分層核心的空間接線，不在 UI 再寫投影／碰撞算法。

## 6. 共用狀態、取消與結果待查

| 狀態 | 結果與允許操作 |
|---|---|
| 編輯中 | 本次輸入未提交；可預覽／取消，沒有上次可用確認按鈕 |
| 預覽中 | 綁專案、原生來源版本與輸入世代；改輸入撤銷本次，晚回覆不覆蓋新輸入 |
| 可確認 | 完整、合法、同來源且同候選；不足是警示，不是幾何失敗 |
| 失效／不完整 | 顯示來源變更、缺件或原生錯誤；保留輸入，不拿舊圖假裝成功 |
| 確認中／結果待查 | 禁止重複確認；依原 requestId 查既有回執，不重送一筆可能已成功的變更 |
| 已提交 | 從正式狀態重讀後才更新 dirty、history、來源／模型工作區及保存資格 |

關閉、Esc、切面／專案、來源更新、Undo/Redo、斷線／重連使 PF 候選失效。關閉後晚回覆不重開，也不改下一份草稿。純 pan／zoom 不改幾何基準。

取消以本次 PF 候選開始基準為界，正式狀態零變更。來源準備的明示獨立提交維持獨立歷史，不混稱本次 PF 的取消回滾。

現行 app.js 的寫入守門、requestId 與 definition-changed 白名單尚未列 panel-fill-confirm。正式接線必須接同一機制，驗掉回覆、重連回執與其他 workspace 變更通知，不能直接新增一顆呼叫原生 confirm 的按鈕就宣稱完整產品。[app.js:615–703][api]

## 7. 新增 transport 契約（提案，不宣稱現有介面）

既有 panel-fill-read／preview／confirm／cancel、POST /panel-fill/preview 及共用候選驗證器保持權威。新 UI 接入須先完成**相應切片**的下列版本化回覆契約；不改幾何定義，不另建第二套求值器。UI-1 不必等 suggest-timbers／from-fill-grid／snapshot 可用；後片再擴充各自能力與欄位，未知能力不猜測。

### 7.1 能力、範圍與完整性

回覆須帶原 schema、來源 revision、明確請求範圍、完整性與支援動作。建議在原回覆新增獨立版本的 uiContract 物件：

- schema：panel-fill-workspace/1（本提案新識別，不是宣稱現有能力）。
- supportedActions：實際可用操作的固定白名單，例如 read、edit-definitions、read-layout、read-support、suggest-timbers、from-fill-grid、export-grid-snapshot；未知值拒絕，不映到相近動作。
- scope：本次明確的 finishSurfaceIds／fillIds；不是目前可見畫布範圍。
- completeForScope：布林；只有所求範圍全部必需資料已完成才為 true。
- errors：具型別錯誤列表，列對象、條號或錯誤碼、期望／實際與缺項，不只有模糊失敗字串。

UI 必須同時核 schema、所需動作、scope、來源 revision、completeForScope 與內層 error。現行全功能 complete:false 不能無條件當全功能完成，也不能只改 true 來啟用 UI。整體 complete:false 與已交付片的 completeForScope:true 可以同時成立，但後者必須有該片完整原生／wire／保存驗收，不能由前端自行推成 true。新版回覆契約的定義與相容測試先行；未支援新 UI 契約時只顯示明確能力限制。

### 7.2 候選與選取鍵

UI-1 沿用既有原生 token／revision，另以本地 generation 隔離晚回覆；不要求尚未交付的 R45 明選鍵。以下集合選取與正式 id 映射屬 UI-2／PF-6 及需要它的後片。

沿用原生 token；每次候選有獨立 generation。候選鍵由原生根據 edge／seam tuple、角色與區間等完整來源產生，只在該 generation 有效。未知、重複或別次鍵拒絕。UI 只送明選鍵與輸入，不拼幾何、不配正式 id。新一輪不能未驗鍵就沿用舊勾選。

每個候選行都有成功／失敗／前置不成立的明確狀態及來源；完整 before／after／changes 覆蓋宿主、主格、角材及所有受影響來源。選取集合變動須重驗依賴，不能只隱藏某條預覽線。

成功提交才回候選鍵到正式 id 的映射。內層 R45 builder 只操作外層 World 候選，不能刪掉 HISTORY_GROUP 守門或巢狀呼叫公共 confirm。

### 7.3 數值與來源分離

完整 typed source 與有效值分欄。所有可能超過 JavaScript 安全整數範圍的整數量，在新版 wire 使用十進位整數字串；精確有理數使用十進位分子／分母字串。座標仍須通過 D1。型別規格逐欄列清，不讓舊 number 欄位悄悄變成另一種型別。

UI 的四捨五入只影響顯示，不能回寫來源或當判定 oracle。需真 C→HTTP→JS 的精確值驗收；Number.isInteger 不能證明沒有丟精度。

來源準備仍依第 3 節明示分步，不把 publish-material／put-parameter 偷塞進僅宣告完成面／試排的交易；已有 PF-H 宿主的 h／B 窄原子更新保留第 2.7 項已交付能力。這些是 R2 §7 點名的工程契約缺口；幾何條文已有答案。[R2][r2]、[panel_fill_bridge:92–139][bridge]

### 7.4 PF6／PF4 的完整 action wire（新增提案，非 main 已有 API）

第一片仍用原 POST /panel-fill/preview 與 panel-fill-transaction/1。後片新增 **POST /panel-fill/actions/preview**，服務端依同樣的有界、嚴格 JSON 輸入規則建立自己的暫存檔，交給擬新增原生命令 **panel-fill-actions-preview <path>**。它只把下列明示動作轉為同一原生候選的 builder；沿用 mode=panel-fill 的 token、確認、取消、過期與回執，不另有 action-confirm 或第二份正式 World。

請求的完整頂層欄位固定為：

| 欄位 | 型別與語意 |
|---|---|
| schema | 固定字串 panel-fill-actions/1 |
| requestKey | 本次前端請求的非空字串；僅做回覆對應，不是物件身分或提交授權 |
| phase | suggest、select、compose 三擇一；只能與下表指定 op 配對 |
| expectedRevision | 原生定義 revision 的十進位無號整數字串，0 至 2^64−1、除 0 外無前導零；新版 wrapper 的固定型別，原 transaction/1 不改型別 |
| owner | 獨立流程為 {"kind":"panel-fill"}；嵌入流程為 {"kind":"candidate","token":"外層不透明令牌","generation":"外層草稿世代","slotKey":"外層登記的插入位置"} |
| scope | {"finishSurfaceIds":[…],"fillIds":[…]}，明列請求根；不重複、action 的 fill 必須在內。完整影響仍沿依賴閉包求得，不能用 scope 隱藏外部影響 |
| action | 依 phase／op 的下列封閉資料型別；未知欄位或操作整筆拒絕 |

所有 id 用 JSON 安全整數，依該既有型別的 uint32／零值合法性檢查；不以 truthy 判斷合法 placement id 0。輸入最多 1 MiB；重複 JSON key、非有限數、NUL、未知 schema／欄位／op、重複選取鍵一律拒絕，不截斷集合。輸出的大整數、有理數沿第 7.3 節。容量沿相應原生能力宣告，超限回具名容量錯誤，不能列部分候選又標完整。

candidate owner 不是瀏覽器自稱即可成立：token 必須屬目前連線、專案、外層候選與其原生來源 revision；generation 與 slotKey 必須是該外層 owner 已登記的當期位置。未知／別人／別專案／舊世代拒絕。獨立流程沒有外層 token，建立唯一 PF 候選 owner；嵌入流程只回到外層候選的同一插入位置，不自行確認。取消 PF 子面板只撤回該位置的未提交提議；外層正式狀態與其他槽位不被暗改。

原生 builder 的固定組合順序為：外層的合法前置操作 → 本 action → 外層後置操作 → 一次完整求值與驗證。builder 不呼叫公開 confirm、不改正式 World、不開始第二個 HISTORY_GROUP。外層任何後置操作非法仍整包拒絕；不能先提交 R45 再等待外層。若外層尚未實作此 owner 能力，回 UNSUPPORTED，不降級成獨立提交。

### 7.5 PF6：建議與明選是兩次不同預覽

**第一階段 suggest。** action 只有以下欄位：

```json
{
  "op": "suggest-timbers",
  "fillId": 1,
  "section": {
    "A": {"kind":"parameter","parameterId":90,"fieldId":2},
    "B": {"kind":"material","id":"stud","version":1,"field":"B"}
  },
  "roles": {"u":"primary","v":"secondary"}
}
```

數值僅為資料形狀例，不是預設來源或自動選擇。section.A／B 各是一份完整既有 dimension source：literal{kind,value}、spec{kind,name}、parameter{kind,parameterId,fieldId} 或 material{kind,id,version,field}；材料必為合法固定 timber 版本，欄位映射按 D7／PF-H 的既有規則驗證。B 用來建立 h 時必須通過 PF-H 的 h 來源規則；不接受 D28 application，不以有效值相等偷換來源。這些來源物件原生編碼已有，只有 action 包裝是新增。[來源 parser:143–166][dimension-source]

roles 必須恰有 u、v 且一個 primary、一個 secondary；u／v 指 D43 縫線的座標軸，其走向由核心轉為 D17 的主支軸，UI 不把「u 軸線」自行當成沿 U 的線。交丁錯開軸必為 secondary；既有主支軸衝突整筆拒絕。宿主與主格按 R45 取得或提議建立，不請前端配 id。

原生以同一基準完整產生 R45 建議，回一份唯讀 proposal：

- setKey 與 generation：此份建議的原生不透明識別；綁 expectedRevision、完整 section／roles、fill、owner 與前置候選內容摘要。
- prerequisites：要重用或新建的 derived-placement、from-fill 主格；新建者只有 tempKey，沒有正式 id。
- entries：每項含 key、kind（boundary／boundary-primary／seam-primary／seam-secondary）、完整 source（衍生 edgeKey 或 fillId／axis／signed k／band）、精確 interval、角色／方向／+n、typed section、status（eligible／rejected）、violations。band 只在所屬型別需要時出現；signed k、band 與大整數採十進位字串。
- omissions：FREE 邊、孔邊、已有覆蓋、不產生候選等逐項原因；它們不能成為可勾選的成功候選。
- completeForScope 與 diagnostics：完整列舉或明確失敗；每項失敗保留原條號，不因某些項成功就說整組可提交。

此階段只供選擇，回覆 token=null、confirmable=false；正式配號／身分帳／World／history／dirty 全不變。即使每項在全建議順序中成立，也不是使用者子集合的合法性證明。

**第二階段 select。** 使用同一 owner、expectedRevision、scope，action 固定為：

```json
{
  "op": "select-timbers",
  "setKey": "原生回傳的 setKey",
  "generation": "原生回傳的 proposal generation",
  "selectedKeys": ["明選的 key 1","明選的 key 2"]
}
```

setKey／generation 不存在或來源已變更即 EXPIRED；未知、重複、rejected 的 key 即 INVALID。使用者不能另附 A/B、定位、角色或新幾何改寫該 proposal。改來源／角色／fill 必須回 suggest，舊 setKey 及其所有候選 token 作廢。

核心從同一正式基準及外層前置操作建立 **fresh 候選**，只套明選集合；依 boundary → 邊界 primary → 縫 primary → secondary、同類依 R45 完整鍵順序重算。某支依賴未選的前支便整組拒絕，不能沿用第一階段已算好的合法幾何、偷補候選或忽略失敗者。空集合回 NO_OP，不為空選取另建宿主／主格。

成功合法且完整時，獨立流程回現有 panel-fill token；嵌入流程回同一 slotKey 的候選操作及完整影響，confirmable 仍為 false，須由外層接入並產生全包新預覽後確認。每次 select 產生新的候選世代、撤銷上一個選取 token；在來源與 owner generation 未變時，相同 proposal 的鍵可用於重選。外層若接受操作而更新 generation，或更改其他槽位，就須重新 suggest，不能跨 proposal／owner generation 使用舊鍵。

### 7.6 PF4：live 主格與普通 D29 快照的資料形狀

兩者都用 phase=compose；不把它們做成可隱性轉型的同一個「網格」按鈕。

**建立活引用主格：**

```json
{
  "op": "create-from-fill-grid",
  "fillId": 1,
  "hostId": 10,
  "mainAlong": "u"
}
```

hostId 必須明指同 fill 的既有 D4 衍生宿主；缺宿主先由 UI-1 明定 h 建立，這個操作不猜 h。mainAlong 必填，可為 u、v 或 null（明示未設）；與既有角材／主支軸的相容仍依原規則。新定義預覽形狀為：

```json
{
  "kind": "grid",
  "tempKey": "原生暫時鍵",
  "hostId": 10,
  "source": {"kind":"from-fill","fillId":1},
  "mainAlong": "u"
}
```

這是 D10 主格，**不是新 D29 系統**；不帶 panel／gap／anchor／stagger／可見線陣列。已有同 fill、同 mainAlong 的主格是 NO_OP，回既有正式 grid id；已有不同來源或不同定義則拒絕並列出，不隱換來源／索引空間。若日後要改既有主格，須走它既有完整編輯契約，不把 create 偷變 put。[D10 from-fill:321–328][from-fill-definition]

**明示導出值快照：**

```json
{
  "op": "export-grid-snapshot",
  "fillId": 1,
  "name": "試排 1 的網格快照",
  "mainAlong": null
}
```

name 必須是 D29 合法非空 UTF-8 名稱；UI 可提議帶來源名稱，但送出前明示，名稱不作身分。mainAlong 同為 u／v／null。此操作不要求 fill 已有宿主；它建立一份獨立普通 D29，沒有暗建 D30 配置或主格。原生回傳新定義：

```json
{
  "kind": "grid-system",
  "tempKey": "原生暫時鍵",
  "name": "試排 1 的網格快照",
  "u": {"kind":"REPEAT_PANEL","panel":"1200","gap":"3","anchor":"0"},
  "v": {"kind":"REPEAT_PANEL","panel":"2400","gap":"3","anchor":"0"},
  "mainAlong": null,
  "stagger": null
}
```

上例數字只示範合法 wire 型別，不是預設值；實際 panel／gap／anchor 由所選 fill 的 P_X／g／a_X 求得，送十進位整數字串，不送公式名稱。交丁時，被錯開軸的 anchor 改成 a_X+δ，stagger 為 {"axis":"u 或 v","value":"−δ 的十進位整數"}，實際 axis 只准 u／v；另一軸保持當下值。映射由核心依 R44／I57 完成，UI 不自行計算。新 D29 只存這些直接整數值，不存 fillId、材料引用、邊界引用、ParameterRef 或有效值之外的第二來源；回覆的 audit provenance 可以顯示源自哪份 fill，但不進其持久定義。後續獨立編輯、D30 配置、signed cell／band 均沿既有契約。[D29:613–642][d29-definition]、[R44][r44]

每次明示導出是新 D29；重複點擊同一次確認依 requestId 回執只能產生一份，不能以名稱相同判為 no-op，也不能因獨立物件內容相同而合併。

### 7.7 共用回覆、確認與正式 id 映射

新 wrapper 回覆 schema 固定 panel-fill-actions-result/1，完整欄位為：requestKey、phase、owner、revision（十進位字串）、scope、status、completeForScope、diagnostics、proposal、candidate。status 是 SUGGESTED／VALID／INVALID／INCOMPLETE／UNSUPPORTED／EXPIRED／NO_OP 之一；不適用的 proposal 或 candidate 明寫 null。diagnostics 每項有 code、clause（無適用條號可為 null）、typed target、message、details；INVALID 等狀態不能帶可確認 token。

candidate 非 null 時，含 generation、token（外層模式為 null）、confirmable、before、after、changes、dependencies、createdDefinitions、reusedDefinitions。before／after 覆蓋外層整包；changes 列新增／修改／刪除及完整來源，dependencies 列影響引用。createdDefinitions 及 R45 entries 只使用 tempKey／候選 key；既有物件才帶其正式 id。NO_OP 不建立可提交 token，不增加 revision／history／dirty。空結果、尚缺資料與合法空幾何分別按原生狀態回報。

獨立合法候選仍經 **panel-fill-confirm <token>**；在同一既有回執新增 actionReceipt（schema=panel-fill-action-receipt/1），欄位固定為 revisionBefore、revisionAfter、generation、committed、idMap、reused。idMap 是 [{key,kind,id}]，涵蓋本次實際新建的宿主、主格、普通角材或 D29；key 對應該候選的 tempKey／entry key，kind 不省略，不能因不同型別同 id 而混配。reused 同形列出既有物件，不能宣稱它們是新建。前端成功後以此映射重讀正式狀態。

正式 id／D59 記號只在成功提交配發；預覽可用私有候選 handle，不占正式配號、不推進身分帳。確認時仍重驗來源、owner 與整包；失敗不留下已配的一半物件。掉回覆只依原 requestId 查回執，不重新執行。候選取消／過期後不得沿 key 查到另一輪物件。

嵌入流程的相同 idMap 由**外層唯一確認回執**交回，並帶 slotKey 供子面板對應；PF 子面板不呼叫 panel-fill-confirm。外層最終成功才標子面板已建立；外層拒絕／取消，所有提議都沒有正式 id 與歷史。這是可組合宿主契約的新增擬文，不聲稱既有 main 已支援外層 action slot。

### 7.8 PF5 沿既有 transaction 的精確更新

PF5 不另發明 action op。空間工作區顯示正式 read 的完成面／宿主，保留原 id 與來源，用原 POST /panel-fill/preview 送完整 panel-fill-transaction/1：

- 改位置／方向／結構側／障礙：{"op":"put-finish-surface","value":{"id":原 id,"name":完整名稱,"boundaryId":明選 D3,"frame":{"origin":[x,y,z],"U":"+X 等軸","V":"+Y 等軸","N":"+Z 等軸"},"structureSide":1 或 -1,"obstacles":["c1","b2"]}}。這是完整替換該定義的值，不把未出現欄位暗當保留；origin 為 D1 整數，三軸通過 D2，obstacles 為已存在 c／b 型別引用。實際送出只能帶合法軸字串，示意中的「等軸」不是 wire 值。
- 改 h：{"op":"put-derived-placement","value":{"id":原宿主 id,"fillId":原 fill id,"h":完整既有來源}}。fillId 不可改指，同 id 不可換成普通 placement；h 同 PF-H 的直接整數或 typed source。
- 若已有角材 B 需隨明選的 h 修改：同一 operations 陣列包含既有 set-source／set-override／unbind-source 或 put-parameter 的完整原格式；逐筆列 before／after dependencies，再一次驗證。不自動改 B，不先單獨提交 h，也不刪角材過關。

所有改動與完整外部依賴在同一候選通過後才確認；不可因面內預覽成功就略過空間撞擊、主格、guide 與既有角材。失敗列具名影響、保留本地輸入，正式 World 不改。純 camera／pan／zoom 不送上述 operations。確認、取消、no-op、保存與更新通知沿 UI-1；新工作是空間入口及完整影響接線。既有欄位與 parser 依 [finish.c:168–238][finish-ops]、[PF-H:8–20、38–45][pfh-whole]。
