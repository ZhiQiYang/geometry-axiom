- **對照**：main 上同一步驟回 200，含 `views`，整支測試通過。
- **原因**：本 PR 讓 `assembly_bridge.inc` 在每個綁定的有效值後面多輸出 `"terminal"`。`geometry-core/rule_cases/executor.py:530` 把 `assembly-read` 的 `state` 原樣放進收據的 `observations`。`rule_case_workbench_adapter.py:185` 的 `_shape(effective, ("value", "path"))` 不收多出來的欄位，於是拒收。
- **實際收據對照**（`observations.before.bindings[0].effective[0]`）：
  - main：`{"slotId": 7, "A": {"value": 27, "path": "explicit integer mm"}, "B": {"value": 33, "path": "explicit integer mm"}}`
  - 本 head：`{"slotId": 7, "A": {"value": 27, "path": "explicit integer mm", "terminal": {"kind": "literal"}}, "B": {…同上加 terminal…}}`
  - 本 head 單一收據內共 8 處 `terminal`；main 0 處。
- **影響**：規則案例工作台產生的收據，同一版本就無法再 `assess` 或 `import`。
- **兩種修法**（暫存補丁採 (a)）：
  - **(a)** 由 executor 投影：`read()` 取得 `assembly-read` 後，移除 `bindings[].effective[].A/B.terminal`。可攜收據格式與舊收據不變；`assembly-read` 本身照樣帶 terminal 給 K1 用。
  - **(b)** 讓 adapter 接受選填的 `terminal`。這等於擴充可攜收據格式：舊版工作台會拒收新收據，需要另外處理版本與相容。
  - 我建議 (a)，因為它符合本 PR `engineering.h` 自己寫的原則（「A NULL terminal leaves every existing caller unchanged」）。最後請審查方決定。

### R354-05／06：同一個根因

- **原因**：`engineering.c`（木工政策）新增 `#include "engineering_sources.h"`，並在 `wood_eng_resolve_terminal`／`wood_eng_effective_terminal` 裡直接呼叫 `wood_engineering_sources_last_terminal(w->sources)`。政策因此依賴來源登記，造成兩個結果：
